# MQ 클라우드 실행기 독립 검토

## 관리되는 AWS 진입점의 축약 옵션 우회 — 수정됨

초기 `aws_wrapper`는 정확한 `--endpoint-url`만 검사했다. 실제 AWS CLI는 `--endp` 같은 축약형도 받아들이므로, 그대로 전달되면 앞에 붙인 소유 endpoint를 덮어쓸 수 있었다. Codex는 생성될 셸 스크립트 원문을 그대로 렌더링하고 실제 설치된 AWS CLI로 이 동작을 재현했다. 목적지는 모두 loopback 테스트 서버였으며 실제 AWS에 접속하지 않았다.

수정은 위험한 전역 옵션의 축약 접두사도 거절한다. 옵션 중복·등호 형태·짧은 접두사·프로필 축약과 정상/생략 endpoint를 실제 CLI로 다시 검사해 8/8이 통과했다. 허용되지 않은 목적지에는 요청이 없었고 정상/생략 입력은 지정한 테스트 endpoint로만 갔다.

원자료: 작업 채팅 폴더 `work/cloud-wrapper-review/result.json`(수정 전 재현), `fixed-results.json`(수정 뒤 8개 검사). 이는 MQ 네이티브 전체 통합 검증과 별개인 정확한 생성 스크립트의 독립 회귀 검사다.

## 사용자 설정 파일 보호 — 수정·단위 검사 추가

실습용 빈 설정 파일은 링크·디렉터리·비어 있지 않은 파일을 거절하고 새 파일은 create_new로 만든다. 버전 조회에도 기본 사용자 AWS 설정 대신 명시적인 빈 장치를 사용한다. 세 Windows 공통 단위 검사와 Unix 링크 검사(Windows에서는 실행하지 않음)를 `config_file_regressions`에 추가했다. 아직 컴파일·실행 결과를 얻기 전이다.

진행 중인 Claude 구현과 독립적으로 이 수정만 반영했다. 기존 소스의 다른 준비·채점 코드는 재작성하지 않았다. 네이티브 컴파일과 실제 Floci 통합 검사는 이어서 수행한다.

## 남은 검토 항목

- 네이티브 실제 검사 helper `report()`가 `check_cloud()`를 직접 호출한다. 적어도 대표 문제 회귀는 실제 제출 경로인 `check_shell()`을 통해 실행해 cloud 분기 연결도 검증해야 한다.
- 네이티브 검사 inventory는 네트워크 ID·이름만 기록한다. 후속 실행에는 전체 network inspect(IPAM·옵션 포함)를 추가해야 한다. 첫 실행의 fixture 검사에서 기본 bridge ID 차이로 실패한 기록은 유지하고, 명령·생성 시각 근거 없이 원인을 단정하거나 차이를 무시하지 않는다.
- AMI 카탈로그가 `architecture: x86_64`로 고정돼 있다. 실제 빌드한 게스트 이미지의 Architecture에서 amd64→x86_64, arm64→arm64를 정해야 한다. Mac 실행 검증을 했다는 뜻은 아니다.
- 주소 파일을 `fs::read`한 다음 256바이트를 검사하므로 실제 읽기 자체는 제한되지 않는다. 일반 파일·링크 여부를 먼저 확인하고 읽기에도 상한을 적용해 잘못된 큰 파일이 앱 메모리를 소모하지 않게 해야 한다. 잘못된 입력 전문을 피드백에 기록하지 않는다.
- 잘못된 CIDR의 서브넷이 하나 있을 때 「필요 없는 서브넷」 실패 항목의 실제 출력이 「추가 서브넷이 없어요」다. 관찰한 상태와 맞는 피드백으로 고쳐야 한다.
- 레지스트리 장애 시 `transfer_image()`의 save/load 파이프라인이 `load.status()`·`saver.wait()`에서 무기한 기다릴 수 있다. 실패한 수신 프로세스 뒤에도 송신기가 남지 않도록 시간 제한과 오류 시 종료·회수를 적용해야 한다. 변경 없는 정상 게스트 검사를 전부 반복하기보다 이 실패 경로를 좁혀 검증한다.
  캐시 전송을 실제로 검증할 때는 새 소유 내부 엔진에 고정 이미지 하나를 직접 save/load하고, create_guest_runtime에서 사용하는 참조·출처 검사까지 되는지 확인한다. archive 전송 뒤 RepoDigests가 유지되는지는 가정하지 않는다. 출처가 검증되지 않은 이미지를 억지로 같은 것으로 간주하지 않는다.

루트가 추가한 `config_file_regressions` 단위 검사(Windows 공통 3개)는 첫 `::tests` 필터 실행에 포함되지 않았다. 컴파일 후 명시적으로 실행해야 한다. Unix 전용 링크 검사는 Windows에서 통과했다고 보고하지 않는다.

## 해결 결과 — 2026-11-10

위 여섯 항목을 수정하고 검증했다. Windows 단위 검사는 설정 파일 3개를 포함해 10개가 통과했다. 제출은 `check_exercise → check_shell → check_cloud`를 실제로 거친다. 네트워크 전체 inspect(IPAM·Options 포함)를 남기고 소유 자원 외의 변화를 숨기지 않는다. 게스트 이미지에서 아키텍처를 읽으며, 주소 파일 읽기와 save/load 파이프라인을 제한한다. 네트워크가 없는 내부 엔진에서 캐시 전송과 내용·출처 검증, Java 실행도 실제 통과했다. 두 개의 처음 실패·재실행 기록은 보존했다.

Codex가 마지막 네 쌍의 원본 호스트 스냅샷을 별도로 처리해 의미상 동일을 확인했다. 컨테이너 Networks 표시 순서 차이만 정렬했고 원본 rawEqual 값도 남겼다. 마지막 소유 자원 0개를 직접 조회했다. 기록은 `target/cloud-native-evidence/codex-native-review.json`이며, 구현·실행 상세는 `docs/floci-cloud-native-runtime.md`에 있다. 본편·Mac·화면·배포가 완료됐다는 뜻은 아니다.
