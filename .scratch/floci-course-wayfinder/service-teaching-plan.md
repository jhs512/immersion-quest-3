# Floci 기반 클라우드 수업 활용 범위와 순서 제안

작성일: 2026-11-09. 상태: **실측을 바탕으로 정리한 추천안**. 학생용 수업 원고나 승인된 PRD가 아니다. 운영 코스·수업·채점기 코드는 변경하지 않았다.

## 정해진 출발점

사용자와 정한 흐름은 기존 네트워크 실습을 유지한 뒤 VPC·서브넷·EC2의 구성·수명주기를 다루고 S3로 이어가는 것이다. 그 이후 순서는 이번 S3·Lambda·데이터베이스 실측을 근거로 제안한다. Mac에서도 같은 동작을 한다는 것은 사용자가 허용한 계획상 가정이며 Mac 실행 검증은 아니다.

코스 배치는 **기존 자바 과정의 후속**으로 사용자와 정했다. 사용자는 이미 있는 네트워크·DB·JDBC 수업의 지식은 안다고 가정하라고 명시했다. 실제 관련 수업 목표·실습을 [기존 수업 연결 근거](existing-curriculum-alignment.md)에 정리했고, 그 기초를 다시 가르치거나 배웠는지 되묻지 않는다. Java용 Lambda·SDK 실행은 별도 미검증 사항이다.

## 판단 기준

- 정상 결과를 먼저 관찰하고 조건 하나를 바꿔 차이를 확인한다. 새 서비스·SDK·자료 모델·이벤트를 한 문제에서 동시에 처음 소개하지 않는다.
- 명령어 문자열을 따라 썼는지보다 객체 바이트, 함수 응답·오류, 실제 DB 행·항목과 상태 변화를 검사한다.
- 각 문제는 자기 준비 자료와 초기 상태를 갖춘다. 이전 문제의 클라우드 자원이 남아 있어야 시작할 수 있게 하지 않는다.
- 실험용 서버·계정·비밀 값과 이미지는 준비된 환경으로 제공한다. 현재 실제로 없는 MQ 이미지·SDK 지원을 구현됐다고 간주하지 않는다.
- 실제 AWS와 에뮬레이터의 차이, 문서 주장과 실측을 구분한다. 대규모 성능·가용성·보안·과금은 로컬 실험으로 보장하지 않는다.

## 서비스별 실측과 활용 판단

| 서비스 | 확인한 실제 결과 | 수업에 쓸 범위 | 이번 증거로 주장하지 않을 것 |
|---|---|---|---|
| S3 | 바이너리·한글·빈 객체의 정확한 바이트, key 덮어쓰기·prefix·잘못된 key, 선택 삭제, 버전·삭제 마커 | key와 객체 본문, 변경·목록·오류·정리. 버전은 기초 뒤 선택 확장 | 모든 S3 API·운영 규모의 내구성·권한. 과거 버전 직접 복원은 이 기본 실행에서 미검증 |
| Lambda | 실제 Python 컨테이너의 입력·출력·예외·timeout, 함수 코드 갱신, 직접 invoke | 함수 실행과 API 호출 성공/함수 성공의 차이. 처음에는 S3·DB 없이 함수 하나 | warm 프로세스 재사용 보장, 전역 변수의 영속성, 운영 성능·IAM 동등성 |
| S3 → Lambda → S3 | incoming 업로드→실제 SDK 읽기→변환된 processed 객체. 수정 입력의 결과 변경과 prefix 음성 대조 | 기존 함수의 수동 호출 뒤 이벤트 연결. 입력과 출력 prefix를 분리 | 유한 시간의 음성 대조로 미래의 미호출을 보장하지 않음. 정확히 한 번 전달 보장은 아님 |
| DynamoDB | 복합 키·자료형·CRUD·Query/Scan, 조건 실패 시 보존, 작은 트랜잭션 성공과 실패 시 보존, 선택 초기화 | 키 중심 접근, 조건부 갱신과 작은 원자성 | 운영 규모 성능·과금·분산 일관성·모든 인덱스/Streams/트랜잭션 조합 |
| RDS PostgreSQL | 실제 PostgreSQL 16.15와 프록시 SQL, CRUD·제약·COMMIT/ROLLBACK, stop/start 자료 보존, 스냅샷 복원 실제 데이터, 원본 삭제 후 복원본 독립 | 관리 API와 실제 DB 준비 상태의 차이, 관리형 인스턴스 수명주기와 자료 상태 | AWS HA·failover·관리형 백업 내구성·AWS VPC 보안·생성 시점의 자동 자원 제한 |

S3 기본·Lambda·이벤트의 완료 실행은 23개 판정을 통과했다. DB는 DynamoDB 범위별 관찰과 별도 RDS 집중 재실행으로 판단했으며 이 항목 수를 같은 단위의 통과 숫자로 합산하지 않는다. S3 영속 모드 재시작·중복 handler 재처리는 별도 보강 실행으로 구분해 기록한다.

### 저장과 재처리 보강

S3에만 persistent 모드를 지정하고 소유 볼륨을 제공한 보강 실행에서는 Floci 프로세스의 정상 재시작 전후 270바이트의 바이너리·한글 데이터가 같은 해시로 읽혔다. memory 모드 재시작의 초기화와 구분한다. 이 실험은 선택한 로컬 저장 설정의 재시작 보존이며 실제 AWS S3의 내구성 보장이 아니다.

같은 대표 S3 이벤트를 handler에 두 번 전달했을 때 두 호출이 성공했고, 정확한 한글 key로 읽은 출력 바이트가 같았다. 원시 판정은 6개 중 5개 통과이며, 나머지는 Windows AWS CLI 목록 stdout을 UTF-8로 해석해 한글 key 문자열 비교가 실패한 것이다. 이를 통과로 덮어쓰지 않았다. 두 목록의 자동 페이지 합산 결과에 객체가 하나씩 있고 같은 정확한 key GET이 성공한 증거로, 관찰 시점에 보이는 결과 객체가 추가되지 않았다는 좁은 결론을 별도로 기록했다. 모든 부수 효과의 멱등성이나 플랫폼의 정확히 한 번 전달을 보장하지 않는다.

### 실행 환경에서 제작 전에 해결할 것

- 기존 MQ는 Floci 이미지나 AWS SDK를 이미 지원하는 상태가 아니다. 실험 하네스를 수업 실행기·자원 소유·초기화·상태 판정 계약으로 옮기는 설계가 필요하다.
- S3 영속 저장과 문제별 초기화를 명시적으로 선택한다. 임의의 서비스 재시작을 실제 AWS 서비스의 자료 소멸로 가르치지 않는다.
- SDK endpoint, 가짜 자격 증명, Lambda 역할·런타임 이미지, RDS 프록시 주소는 준비된 실행 환경의 책임이다. 첫 문제에서 여러 설정을 학습자에게 한꺼번에 요구하지 않는다.
- 한글 CLI 출력의 인코딩을 고정·검증한 뒤 목록 화면에 사용한다. 정확한 객체 바이트 검증과 화면 문자열 비교를 구분한다.
- privileged DIND는 이번 연구 구성이다. 개별 게스트의 생성 시점 제한과 정리·포트·보안 경계를 실제 MQ 실행 환경에서 따로 검증한다.
- S3 준비 실패 실행 하나에서 기본 bridge의 ID·생성 시각 변경이 관찰됐다. 사용자 정의 네트워크·컨테이너·볼륨은 보존됐지만 원인은 미확인이다. 정상 완료 실행·보강 실행의 전후 목록은 같고, 보강에서는 bridge IPAM/options를 포함한 inspect도 같았다. 모든 시도에서 호스트가 완전히 불변이었다고 주장하지 않는다.

## 추천 순서

기존 자바·네트워크·DB·JDBC 수업 지식을 아는 MQ 학습자를 기준으로 한 제안이다. 모든 서비스를 처음부터 필수로 연결한 하나의 앱을 만들지 않는다.

| 순서 | 수업 묶음 | 처음 관찰할 최소 예제 | 그다음에 더할 것 |
|---|---|---|---|
| 1 | VPC·서브넷·EC2 | 주소 공간 안에 서버 한 대 배치 | 잘못된 대역, 중지·재시작·종료, 삭제 의존성 |
| 2 | S3 객체 저장 | 값 하나를 같은 key로 쓰고 읽기 | key 하나 변경, 덮어쓰기·목록·없는 key·선택 삭제 |
| 3 | RDS 관리형 DB | 준비된 SQL 한 번을 별도 DB에 실행 | API available과 실제 SQL 준비, 중지·재시작 보존, 스냅샷 시점 비교 |
| 4 | Lambda 독립 실행 | 함수 하나에 값을 넣고 결과 읽기 | 잘못된 입력·함수 예외, 코드 갱신, timeout을 각각 분리 |
| 5 | Lambda에서 S3 사용 | 직접 invoke로 객체 하나 읽고 결과 쓰기 | SDK 준비는 제공하고 key·변환식의 작은 변경만 관찰 |
| 6 | S3 이벤트 연결 | 업로드가 기존 함수를 실행하도록 연결 | prefix 변경, 입력/출력 분리, 재처리 효과는 별도 검증 후 추가 |
| 선택 후속 | DynamoDB 자료 접근 | SQL 없이 정확한 key로 항목 하나 조회 | 복합 키·Query/Scan·조건부 쓰기·원자성 순으로 분리 |

이 순서에서 RDS가 Lambda의 기술적 필수 조건은 아니다. 이미 아는 SQL·JDBC를 서버 밖의 관리형 서비스로 옮기는 경험을 EC2/S3 뒤에 연결하려는 교육적 배치다. 이 후속 묶음에서 SQL 입문을 다시 끼우지 않는다. DynamoDB도 RDS와 모두 필수로 외울 서비스 목록이 아니라 **새 자료 접근 모델을 비교하고 싶을 때** 선택한다.

Lambda의 이번 실제 실행 언어는 Python 3.12다. 함수·JSON을 먼저 익혔거나 준비 단원으로 제공해야 하며, Java 학습자에게 새 언어 문법·SDK·이벤트를 동시에 요구하지 않는다. Java Lambda나 Java AWS SDK로 바꾸려면 그 런타임·의존성·동작을 별도로 검증한다. 이번 Python 성공을 다른 언어의 검증 완료로 간주하지 않는다.

S3 버전 관리·RDS 스냅샷·DynamoDB 트랜잭션은 첫 문제에 동시에 넣지 않는다. 각각 덮어쓰기 손실·복구 시점·중간 변경의 문제를 먼저 관찰한 뒤 추가한다. RDS의 PK·CHECK·SQL 트랜잭션은 기존 SQL 수업을 되풀이하는 핵심 목표로 삼기보다, 관리형 DB에서도 동일한 자료 규칙이 유지되는지 확인하는 선수 복습으로 쓴다.

## 순서를 정할 때 구분할 축

| 축 | 먼저 확인할 최소 원리 | 뒤에 연결할 경험 |
|---|---|---|
| S3 | bucket·key와 객체 바이트, 같은 key 변경 | 버전·삭제·별도 저장소와 서버 수명주기의 차이 |
| Lambda | 함수 하나의 입력과 출력, 실행 오류 | 함수 수정·재실행, 외부 서비스 호출, 이벤트 실행 |
| RDS PostgreSQL | 이미 배운 SQL을 별도 DB 서버에 연결 | 관리형 인스턴스 상태와 실제 SQL 상태·자료 보존의 차이 |
| DynamoDB | 키로 항목을 저장·조회 | 복합 키와 Query·Scan, 조건부 갱신, 원자성 |
| S3 → Lambda | 두 서비스를 각각 이해한 뒤 이벤트로 연결 | 중복·재실행에 견디는 처리와 결과 객체 검증 |

RDS는 새 SQL 문법을 처음부터 다시 가르치는 단계가 아니다. 기존 SQL·컨테이너·접속 경험을 관리형 서비스의 구성과 수명주기로 연결하는 후보이다. DynamoDB는 같은 DB 서비스를 하나 더 외우는 단계가 아니라 다른 자료 접근 모델을 배우는 후보이다. 둘을 초급자의 필수 연속 단계로 묶을지는 실측과 선수 경험을 근거로 정한다.

S3 이벤트의 실제 AWS 의미는 최소 한 번 전달이며 순서가 보장되지 않는다. 한 실험에서 한 번 실행됐다는 이유로 정확히 한 번 실행되는 플랫폼이라고 가르치지 않는다. 멱등성은 같은 입력을 재처리해도 의도한 상태가 유지되는 애플리케이션 성질과 구분해 확인한다. 근거: [Amazon S3 Event Notifications](https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html), [AWS의 중복·순서 설명](https://aws.amazon.com/blogs/storage/manage-event-ordering-and-duplicate-events-with-amazon-s3-event-notifications/).
