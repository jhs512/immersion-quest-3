## 1. 수업 교육 목표

- 이미 아는 CIDR로 VPC와 서브넷의 포함 관계를 읽고 선언한다.
- 서버(EC2 인스턴스) 한 대를 지정한 서브넷에 배치하고, 받은 사설 주소가 그 서브넷 범위 안인지 확인한다.
- 같은 VPC의 다른 서버에서 그 주소로 HTTP 응답을 받아 배치를 확인한다.

중심 질문: **이미 아는 서버를 어느 주소 공간·서브넷에 배치할 것인가.** 세 목표는 「선언된 자원 관계와 서버 배치」라는 하나의 목표의 단계다.

## 2. 대상과 위치

- 기존 자바 과정을 마친 학습자. 독립 클라우드 코스가 아니라 자바 과정의 후속 클라우드 묶음 첫 수업이다.
- 사용자 결정(2026-11-09): 네트워크·SQL·JDBC·Compose·자바 파일/예외 실습 지식은 안다고 전제한다. 선수 지식을 다시 묻는 진단·복습 수업을 만들지 않는다.
- 다음 수업: EC2 수명주기(중지·재시작·종료)와 삭제 의존성. 그다음 S3([추천 순서](../service-teaching-plan.md)).

## 5. 조사 근거 (내부)

- [06 VPC·서브넷·EC2 실험](../issues/06-vpc-subnet-runtime-experiments.md): 공식 Floci 2.4.0을 Windows Docker Desktop의 격리 DIND 엔진에서 실행. VPC/서브넷 생성·조회, 범위 밖/중첩/너무 작은 서브넷·예약 IP 거절, 삭제 의존성, 기본 모드에서 API 사설 IP = 실제 Docker IP, 같은 VPC(같은/다른 서브넷) HTTP marker 통신, 실제 수명주기 확인.
- 같은 실험의 한계: 라우팅·NACL·NAT·피어링은 AWS 패킷 동작과 같다고 입증하지 못함. SG 선택 모드는 transport 주소에서만 효과, API 사설 IP 연결은 실패. 다른 VPC 사설 IP는 실패했으나 공통 bridge IP로는 도달.
- Mac 동일 동작은 계획상 가정이며 실측이 아니다.

학생 본문에는 실행 ID·해시·Docker 내부 구성을 쓰지 않는다. 학생에게는 「로컬 실습 환경이고 확인한 동작만 다뤄요」 수준으로만 알린다.

## 6. 교육 원칙 (이 수업에 적용)

- 한 스텝에 새 개념 하나. 새 외부 서비스는 이 수업 전체에서 Floci(로컬 AWS 호환 API) 하나다. EC2 게스트는 2장에서 처음 쓴다.
- 학생 수정은 1~3줄, 대부분 값 한 곳. 새 옵션·설정량을 난도로 쓰지 않는다. 난도는 「어느 범위·어느 자리」의 판단으로 올린다.
- 모든 채점 스텝은 직접 명령을 실행하고 실제 상태로 판정한다. 객관식·결과값 입력 없음.
- 모든 스텝은 독립 초기 상태로 시작한다. 준비 자원은 시작 상태 설명에서 먼저 알리고 학생이 만든 것처럼 쓰지 않는다.
- 모든 AWS CLI 명령은 `--endpoint-url "$LAB_ENDPOINT"`를 명시한다. 실제 AWS를 부르지 않는다.
- 학생이 자원을 확인할 때는 `describe-*`의 일반 출력을 읽는다. 채점용 `--query`·필터 조합을 필수 명령으로 노출하지 않는다. 필요한 필터는 준비 명령으로 제공한다.

## 7. 구성 — 챕터 → 단원 → 스텝

표기: **새** = 새 개념, **기존** = 이미 배운 것, **행동** = 작은 행동, **관찰** = 실제로 볼 것, **오답** = 대표 오답과 판정 근거, **시작** = 독립 초기 상태.

### 챕터 1. 주소 공간을 선언해요

챕터 목표: VPC가 주소 공간 하나를 선언한 자원이고, 서브넷은 그 안의 겹치지 않는 범위라는 관계를 실제 생성·거절로 확인한다.

핵심 흐름: 준비된 VPC를 읽는다 → 그 안에 서브넷을 하나 만든다 → 밖의 범위가 거절되는 것을 보고 고친다 → 이미 있는 범위와 겹치지 않게 고른다.

#### 단원 1.1 준비된 주소 공간 읽기

단원 목표: 실습 환경이 준비한 VPC의 ID와 CIDR을 API로 읽고, 그 범위를 이미 아는 IPv4 표기로 해석한다.

**스텝 1.1.1 준비된 VPC의 주소 공간을 읽어요** (실행·관찰, 채점 없음)

- 목표: VPC가 CIDR 하나를 가진 자원임을 조회 결과로 확인한다.
- 시작: VPC `10.91.0.0/16` 하나, 서브넷 0개. `LAB_ENDPOINT`·연습용 자격 값·리전·`LAB_VPC_ID` 준비.
- 새: VPC = 선언된 주소 공간 자원(VpcId·CidrBlock·State).
- 기존: `/16`이 앞 두 칸을 고정한다는 IPv4 판단.
- 행동: 준비 명령 `aws ec2 describe-vpcs --endpoint-url "$LAB_ENDPOINT" --vpc-ids "$LAB_VPC_ID"` 실행.
- 관찰: `CidrBlock`, `VpcId`, `State`.
- 오답: 채점이 없다. 해설에서 「`--endpoint-url`을 빼면 실제 AWS 주소로 가려 해요. 조심하세요」를 말로 짚는다(실제로 쳐 보지 않는다).
- 비고: 채점할 행동이 없으므로 가짜 채점 단계로 만들지 않는다.

#### 단원 1.2 VPC 안에 서브넷 만들기

단원 목표: 서브넷이 VPC 범위의 일부여야 하고, 같은 VPC 안에서 겹칠 수 없다는 규칙을 생성 성공·거절로 확인한다.

단원의 이어지는 상황: 같은 준비 VPC `10.91.0.0/16`. 스텝마다 서브넷 조건만 달라진다.

**스텝 1.2.1 준비 명령으로 서브넷 하나를 만들어요**

- 목표: 서브넷이 VPC에 속한 하위 범위 자원임을 생성 결과로 확인한다.
- 시작: VPC만 있음, 서브넷 0개. 준비 명령은 이미 올바른 값 `10.91.1.0/24`.
- 새: 서브넷 = VPC 안의 하위 범위(SubnetId·VpcId·CidrBlock).
- 기존: 1.1.1의 VPC 조회.
- 행동: 준비된 `create-subnet` 실행 → `describe-subnets` 실행.
- 관찰: 결과의 `VpcId`가 준비 VPC와 같고 `CidrBlock`이 `10.91.1.0/24`.
- 채점: 소유 VPC에 `10.91.1.0/24` 서브넷 정확히 하나, `available`.
- 오답: 다른 VPC를 만들어 그 안에 생성 → 소유 VPC 서브넷 0개로 실패.

**스텝 1.2.2 범위 밖 서브넷을 VPC 안으로 옮겨요** — 대표 문제

- 목표: VPC 밖 범위는 거절되고, 범위를 VPC 안으로 고치면 생성된다는 것을 확인한다.
- 시작: VPC만 있음, 서브넷 0개. 준비 명령의 CIDR이 `10.92.2.0/24`.
- 새: 범위 밖 서브넷의 거절.
- 기존: `network-ip`의 범위 안/밖 판단, 1.2.1의 생성.
- 행동: 원본 실행(거절) → CIDR 한 곳을 `10.91.2.0/24`로 수정 → 재실행 → 조회.
- 관찰: 원본의 실제 오류 메시지, 수정 후 `CidrBlock`·`VpcId`·`State`.
- 채점·오답: [대표 문제 초안](representative-problem.draft.md)의 계약 그대로.

**스텝 1.2.3 이미 있는 서브넷과 겹치지 않게 골라요**

- 목표: 같은 VPC 안의 서브넷끼리는 범위가 겹칠 수 없음을 거절로 확인하고, 겹치지 않는 범위를 직접 고른다.
- 시작: VPC + 준비 서브넷 `10.91.1.0/24`(준비 스크립트가 만든 것이라고 먼저 알림). 준비 명령의 CIDR은 `10.91.1.128/25`.
- 새: 같은 VPC 안 서브넷 범위의 겹침 거절.
- 기존: 1.2.2의 범위 밖 거절(안이어도 거절되는 다른 이유).
- 행동: 원본 실행(거절) → `describe-subnets`로 기존 범위 확인 → `/25` 값 한 곳을 VPC 안·기존과 겹치지 않는 범위로 수정 → 재실행.
- 관찰: 겹침 오류 메시지, 수정 후 두 서브넷의 범위.
- 채점: 소유 VPC에 준비 서브넷 그대로 + 새 `/25` 하나. 새 범위는 `10.91.0.0/16` 안이고 `10.91.1.0/24`와 겹치지 않음. 특정 값 하나를 정답으로 고정하지 않는다(동등한 유효 풀이 허용).
- 오답: 준비 서브넷을 지우고 `10.91.1.128/25` 생성 → 준비 서브넷 변경으로 실패. `/24` 등 다른 크기 → 지시와 다름으로 실패. 범위 밖 값 → 거절.

### 챕터 2. 서버 한 대를 서브넷에 놓아요

챕터 목표: 인스턴스는 서브넷 하나에 놓이고 사설 주소를 그 서브넷에서 받는다는 것, 같은 VPC의 다른 서버가 그 주소로 요청할 수 있다는 것을 실제 실행으로 확인한다.

핵심 흐름: 지정한 서브넷에 서버를 띄운다 → 받은 주소가 서브넷 범위 안인지 읽는다 → 엉뚱한 자리에 놓이는 명령을 고친다 → 같은 VPC의 다른 서버에서 그 주소로 응답을 받는다.

이 챕터의 서버 이미지는 실측된 작은 HTTP marker 서버(준비 제공)다. 학생은 이미지 내용을 다루지 않는다.

#### 단원 2.1 서버의 자리는 서브넷이에요

단원 목표: `run-instances`의 서브넷 지정과 결과 인스턴스의 SubnetId·VpcId·PrivateIpAddress의 관계를 읽는다.

단원의 이어지는 상황: VPC `10.91.0.0/16`과 준비 서브넷 두 개 `10.91.1.0/24`(`LAB_SUBNET_A_ID`), `10.91.2.0/24`(`LAB_SUBNET_B_ID`). 둘 다 준비 스크립트가 만들었다고 먼저 알린다.

**스텝 2.1.1 지정한 서브넷에 서버 한 대를 띄워요**

- 목표: 인스턴스가 지정한 서브넷에서 사설 주소를 받는 것을 확인한다.
- 시작: 위 VPC·서브넷, 인스턴스 0개. 준비 명령은 `--subnet-id "$LAB_SUBNET_B_ID"`.
- 새: 인스턴스 = 서브넷에 놓이는 서버 자원.
- 기존: Docker로 이미지에서 서버를 띄운 경험, 1장의 서브넷.
- 행동: 준비된 `run-instances` 실행 → `describe-instances` 실행.
- 관찰: `SubnetId`, `VpcId`, `PrivateIpAddress`(10.91.2.x), 상태 변화(`pending`→`running`, 기다림 필요).
- 채점: 소유 VPC·서브넷 B에 실행 중 인스턴스 하나, 사설 주소가 `10.91.2.0/24` 안.
- 오답: 실행 직후 `pending`만 보고 제출 → 채점은 `running`까지 기다리는 정해진 시간 안의 상태를 읽고, 시간 안에 안 되면 「아직 시작 중이에요」로 실패. 해설의 「조심하세요」: 요청 성공과 실행 완료는 다르다(Docker 비동기 상태 경험 연결).

**스텝 2.1.2 엉뚱한 서브넷에 놓이는 명령을 고쳐요**

- 목표: 같은 VPC 안에서도 서브넷 선택이 서버의 자리와 주소를 정한다는 것을 확인한다.
- 시작: 2.1.1과 같은 VPC·서브넷, 인스턴스 0개. 준비 명령은 `--subnet-id "$LAB_SUBNET_A_ID"`. 목표는 `10.91.2.0/24`에 배치.
- 새: 배치 자리 선택(같은 VPC 안 서브넷의 차이).
- 기존: 2.1.1의 인스턴스 조회.
- 행동: 원본 실행 → 받은 주소가 목표 범위 밖인 것을 관찰 → 「다시 시작」으로 독립 초기 상태 복원 → 서브넷 변수 한 곳 수정 → 재실행.
- 관찰: 원본의 `10.91.1.x`, 수정 후의 `10.91.2.x`.
- 채점: 소유 VPC에서 실행 중 인스턴스는 서브넷 B의 하나뿐. 서브넷 A에 실행 중 인스턴스가 남아 있으면 실패.
- 오답: 서브넷 A 인스턴스를 남김 → 오배치 자원으로 실패. 다른 VPC 서브넷 지정 → 실패.
- 제작 조건: 「다시 시작」이 초기 자원과 준비 파일을 복원해야 한다. 종료 명령을 학생에게 추가로 가르치지 않고 자리 선택 한 곳에 집중한다.

#### 단원 2.2 같은 VPC 안에서 서버에 요청해요

단원 목표: API가 알려 준 사설 주소로 같은 VPC의 다른 서버가 실제 HTTP 응답을 받는다는 것을 확인한다.

**스텝 2.2.1 다른 서브넷의 서버에서 사설 주소로 요청해요**

- 목표: 같은 VPC의 다른 서브넷에서도 API 사설 주소로 서버에 닿는다는 것을 확인한다.
- 시작: VPC, 서브넷 A·B, 서브넷 B의 marker 서버, 서브넷 A의 준비 클라이언트 인스턴스(모두 준비 스크립트가 만듦). 학생은 클라이언트 안에서 명령을 실행하는 준비 진입 명령을 받는다.
- 새: API가 알려 준 사설 주소 = 같은 VPC에서 연결할 주소.
- 기존: `network-http`의 요청·응답 읽기, `network-routing`의 다른 네트워크 구별.
- 행동: `describe-instances`로 서버 사설 주소 읽기 → 준비된 요청 대상 파일의 주소 한 곳을 그 주소로 수정 → 제공된 HTTP 요청 명령 실행.
- 관찰: HTTP 응답 본문의 marker 문자열.
- 채점: 요청 대상 파일의 주소 값과 소유 서버의 API 사설 주소를 비교한다. 채점기가 소유 클라이언트에서 자체 HTTP 클라이언트로 새 요청을 보내 소유 서버의 응답을 검증한다. 학생 스크립트·stdout 재실행을 성공 증거로 삼지 않는다. 대상 파일 형식·서버 응답 검증·실행 위치는 제작 전 검증 대상이다.
- 오답: API에 없는 Docker bridge 주소 → 주소 불일치로 실패. 주소가 틀린 채 `echo`로 성공 문자열만 출력 → 실제 주소 검사와 독립 HTTP 요청에서 실패.
- 비고: 다른 VPC로의 통신 차단은 다루지 않는다. 실측에서 공통 bridge 주소로 닿는 경로가 있어 「다른 VPC는 막힌다」를 가르칠 근거가 없다.

### 챕터 3. 기존 자바 서버를 배치해요

챕터 목표: 앞에서 확인한 관계를 그대로 써서, 기존 자바 과정의 HTTP 서버를 지정한 서브넷에 배치하고 같은 VPC에서 응답을 받는다.

핵심 흐름: 서버 이미지만 기존 자바 서버로 바뀐다 → 학생이 배치 서브넷과 요청 주소를 스스로 정한다 → 응답으로 확인한다.

#### 단원 3.1 마지막 수행

단원 목표: 새 개념 없이 1·2장의 판단(범위·자리·주소)을 조합한다.

**스텝 3.1.1 자바 서버를 10.91.2.0/24에 배치하세요** — 제작 전 게이트

- 목표: 이미 아는 자바 서버를 원하는 서브넷에 놓고 같은 VPC에서 응답을 받는다.
- 시작: VPC `10.91.0.0/16`, 준비 서브넷 A `10.91.1.0/24`와 클라이언트, 자바 서버 이미지(준비 제공). 목표 서브넷 `10.91.2.0/24`는 아직 없으며 학생이 만든다.
- 새: 없음(조합).
- 기존: 1.2.2 서브넷 생성, 2.1 배치, 2.2 요청.
- 행동: 서브넷 생성 명령의 CIDR → `run-instances`의 서브넷 → 요청 주소를 각각 한 곳씩 채움(세 곳).
- 관찰: 자바 서버의 응답.
- 채점: 소유 VPC에 `10.91.2.0/24` 서브넷 하나, 그 서브넷에 자바 서버 인스턴스 실행 중, 클라이언트에서 그 API 사설 주소로 응답.
- 오답: 서브넷 A에 배치, 다른 VPC에 배치, 응답 출력 위조.
- **게이트**: 자바 서버를 EC2 게스트에서 실행한 시험이 없다. 지금 실측된 것은 Alpine/BusyBox marker뿐이다. 게이트가 통과하지 않으면 이 스텝을 marker 서버로 바꾸고 예고의 최종 수행 문장을 고쳐 다시 승인받는다.

## 9. 채점 원칙 (모든 채점 스텝)

- 채점기는 스텝 초기화의 **소유 기록**(VPC ID·서브넷 ID·목표 CIDR)을 기준으로 실제 상태를 읽는다. 학생 셸 변수·명령 문자열·터미널 출력은 근거가 아니다.
- 소유 범위 밖 자원은 통과 근거가 되지 않는다. 같은 CIDR이라도 다른 VPC면 다른 자리다.
- 정답이 하나로 정해지지 않는 스텝(1.2.3)은 조건을 검사한다.
- 비동기 상태는 정해진 시간 안의 안정 상태로 판정한다. sleep 길이를 정답으로 삼지 않는다.
- 이 채점 계약은 **MQ에 구현되지 않았다.** 설계안이다.

## 10. 초기화

- 스텝마다 새 Floci 상태(메모리 모드)에서 준비 스크립트를 실행한다. 앞 스텝 답안의 자원에 의존하지 않는다.
- 준비 스크립트가 만든 VPC·서브넷·인스턴스는 시작 상태 설명에서 먼저 알린다.
- 「다시 시작」은 Floci 상태와 준비 파일을 원래대로 돌린다.
- 해설 시연은 학생 상태를 보존한 별도 실습 상태에서 한다(`docs/content-rules.md` 「문제 정체성과 성취」).

## 11. 검증 기준 (제작 시)

각 채점 스텝마다 실제 실행으로 남긴다: 대표 정답 통과, 준비 코드 실패, 개념 오해 오답 실패, 동등 유효 풀이 통과, 준비 값을 바꾼 변형(예: VPC `10.73.0.0/16`) 통과·실패 재현. 그 뒤 `python tools/build-kpc-course.py` 등 레포의 기존 빌드 검사를 통과해야 한다. 해설은 `docs/agents/narration.md`와 `python tools/narrate.py` 절차를 따른다(본편 승인 뒤).

## 12. 기술 준비 (내부 · 학생에게 노출하지 않음)

### 실측으로 확인된 것 (06 실험, Windows 격리 DIND, 공식 Floci 2.4.0)

- VPC·서브넷 생성·조회, 범위 밖/중첩/너무 작은 서브넷·예약 IP 거절, 삭제 의존성.
- 기본 모드에서 API 사설 IP와 실제 컨테이너 IP 일치, 같은 VPC 같은/다른 서브넷의 HTTP marker 통신.
- 실제 EC2 상태(stopped·Running=false, start 후 복구, terminate 후 제거).
- 모든 AWS CLI 호출이 명시적 loopback endpoint 사용.

### 제작 전 게이트 (미검증 · 해결 전 본편 제작 금지)

1. **자바 서버 게스트 실행**: 기존 자바 HTTP 서버를 EC2 게스트로 올려 같은 VPC에서 응답받는 시험이 없다. 3.1.1의 전제다.
2. **MQ 통합 없음**: Floci 이미지 실행기, 스텝별 자원 소유 기록, 상태 채점, 초기화·다시 시작, 해설 시연용 별도 상태가 MQ에 없다.
3. **보안 경계**: Floci EC2는 기본으로 SSH 포트를 호스트에 자동 공개한다. 실험은 그래서 privileged DIND로 격리했다. privileged DIND를 학생 멀티테넌트 보안 경계로 약속하지 않는다. MQ 실행 환경의 격리·포트 정책을 따로 정해야 한다.
4. **외부 AWS 차단**: `--endpoint-url`을 지운 명령이 실제 AWS로 나가지 않도록 실행 환경에서 막고, 그 실패를 채점이 「로컬 상태 변화 없음」으로 처리하는지 확인한다.
5. **예약 IP 거절 경로**: 실험의 예약 IP 거절이 어느 API 경로였는지 확인한다. 이 초안은 예약 IP를 스텝으로 쓰지 않았다.
6. **2.2.1 진입·독립 통신 검증**: 학생의 클라이언트 진입 방법, 요청 대상 파일 형식, 채점기 자체 HTTP 요청·소유 서버 응답 검증을 구현하고 출력 위조 오답으로 확인한다. 실험은 API 사설 IP 연결을 기본 모드에서만 확인했다.
7. **Mac**: 동일 동작은 계획상 가정이며 실측하지 않았다.
8. **운영 등록 정보**: 새 `proposed_lesson_key`, 자바 과정 카탈로그 `core_flow`의 위치와 `course_intent_sha256` 영향은 승인 뒤 정한다. 기존 Docker 선수 수업의 키·제목은 대조했다.

### 주장하지 않는 것

- 라우팅 표·IGW·NAT·NACL·피어링의 AWS 패킷 동등성.
- 보안 그룹 효과의 API 사설 IP 경로 동작.
- 다른 VPC 간 완전 격리.
- 기존 자바 서버·AWS SDK·Java Lambda 동작.
- 실제 AWS와의 성능·가용성·과금·보안 동등성.
