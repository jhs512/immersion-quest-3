# GitLab 실습 전환과 CI/CD 수업

사용자 지시: 기본 GitHub를 쓰는 수업을 모두 GitLab으로 전환하고 워크플로 수업을 기획·제작·추가한다. 실습에서 회원가입·로그인·토큰 입력을 요구하지 않는다. GitHub 검증 보류는 외부 GitHub 테스트 저장소 생성을 계속 금지한다.

## 범위와 순서

1. Git 기초·리모트·MR 수업의 학생 노출 내용과 실제 호스팅 의존을 조사한다. 코스 다운로드·사용자 진도 저장 등 앱 자체의 GitHub 전송 계층은 실습 플랫폼과 구분해 유지한다.
2. 이미 검증한 로컬 GitLab을 앱에서 재현할 수 있도록 패키징한다. 고유 이름·빈 포트·루프백 바인딩을 사용하고 실습 전용 일반 계정은 내부에서 자동 연결한다. 공식 glab CLI를 사용한다.
3. 기존 PR 수업을 실제 GitLab 프로젝트·브랜치·MR·diff·병합 확인으로 전환한다. 기존 수업 코드와 동일 개념의 단계 코드는 보존하며 개정 번호를 올린다. 새 종합 도전은 신규 코드로 만든다.
4. GitLab CI/CD 수업을 추가한다. 명령 직접 실행 → 같은 명령을 script에 넣기 → push로 파이프라인 실행 → 실패 로그 → 수정 후 재실행 → stages 순서 → artifacts 전달 → 조건부 실행 → 종합 도전 순으로 하나씩 쌓는다.
5. GitLab Runner가 실제 Docker 작업 컨테이너를 실행하게 한다. 성공/실패·커밋 SHA·작업 로그·산출물을 실제 API로 채점한다. 로컬 명령 실행을 원격 파이프라인 성공으로 위장하지 않는다.
6. MR 전 과정·오답 거절·실패/복구 파이프라인·종합 도전·진도 호환을 검증한다. 해설은 문제 소개부터 시작하고 실행 결과와 정확히 일치시킨다.
7. 메인 병합·푸시, 필요한 앱 배포와 독립 수업 게시, 공개 데이터 확인까지 진행한다. 새 실행기를 모르는 구 앱에는 새 수업을 먼저 게시하지 않는다.

## 제약

- 기존 개발자의 컨테이너·포트·Git 자격 증명·저장소를 변경하지 않는다.
- 관리자 토큰을 학생 터미널에 주지 않는다. 실습 계정은 로컬 실습 전용이다.
- 학생 작업 컨테이너에는 Docker 소켓·호스트 폴더·privileged 권한을 제공하지 않는다.
- Runner 관리에 필요한 Docker 소켓은 관리용 Runner에만 연결하고 작업 이미지를 제한한다.
- 학생에게 GitHub Actions와 GitLab CI/CD를 혼용해 설명하지 않는다. 이 과정의 파일은 `.gitlab-ci.yml`, 코드 검토는 MR이다.
