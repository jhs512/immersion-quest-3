# 셸 변수·환경 수업, 수업별 진도 초기화, 도전 과제 클리어 (2026-10-29 계획)

사용자 요청(Codex 경유, 2026-10-29): 셸 변수·환경 변수·명령 한 번의 환경 지정·실행 인자 수업을 만들어 자바 백엔드 과정에 넣고, 필요하면 순서를 고치고, 학습자가 수업 하나의 진도를 직접 초기화하고, 마지막 도전 과제를 통과하면 문제를 건너뛰었어도 그 수업을 클리어하게 한다. 사용자는 계획을 저장한 뒤 별도 승인 없이 진행하라고 했다. 이 문서가 그 계획이며, 수업 PRD 승인 근거로 기록한다. Cloudflare D1은 개념 질문이었고 이번 범위가 아니다.

## 1. 현재 구현에서 확인한 사실

- 진도는 이벤트 로그다(`src/issue_progress.rs`). 로컬 SQLite·대기 파일·GitHub 이슈 댓글을 id로 합집합(`merge`)하며 아무것도 지우지 않는다. 업로드 확인(`acknowledge_batch`)은 원격 합집합에 보낸 이벤트가 있는지로 판단한다. 따라서 초기화는 이벤트 삭제로 구현할 수 없고, 지우면 다음 동기화가 되살린다.
- 완료 이벤트 id는 `completed:계정:코스:수업:버전:모드:회차`로 고정이다. 같은 회차에서 초기화 뒤 다시 완료하면 같은 id가 되어 새 완료가 기록되지 않는다.
- 수업 완료는 필수 문제 전부 통과(`status`)다. 게이지는 `learning_progress`(통과 수/필수 수)다.
- 도전 과제 화면(`src/challenges.rs`)은 수업마다 "마지막으로 채점하는 문제"를 추정해 모으고 "종합 문제 검토 전"이라고 표시한다. 명시적 지정은 없다.
- 공개 40수업 중 마지막 문제가 실제로 종합·전이 문제인 수업과, 단순히 마지막 연습인 수업이 섞여 있다(예: bash-basics의 마지막은 `rm -r` 연습, sql-transactions의 마지막은 종합 도전).
- Bash 실습은 실제 PTY Bash(`--noprofile --norc`)다. 스텝을 바꾸면 셸이 새로 시작한다(`docs/curriculum/bash-environment-foundations.md`의 미해결 계약). 채점은 스텝 시작 이후 성공한 명령의 순서(`commands`)와 폴더의 실제 파일·폴더·현재 위치다. 자바 실행은 같은 셸에서 앱 래퍼를 거쳐 실제 JDK를 실행하며 셸의 환경을 그대로 물려받는다.
- 앱은 코스·수업을 실행 파일에 포함하고(`bundled_courses.rs`), 원격 코스가 오면 그것을 따른다. `LessonRef`는 모르는 필드를 거절하지 않으므로 이전 앱은 새 코스 필드를 무시한다.
- 공개 대시보드(`site/dashboard/model.mjs`)도 같은 이벤트를 읽어 통과를 센다.

## 2. 수업: 3개, 기존 실행기만 사용

셸이 스텝마다 새로 시작하는 것은 결함이 아니라 이 주제의 관찰 대상으로 쓴다. 각 스텝은 자기 Bash에서 처음부터 끝까지 이어지는 짧은 실험이며 시작 상태(새 셸, 제공 파일)를 먼저 알린다. 앞 스텝의 변수가 남는다고 암시하지 않는다. 새 실행기·가짜 해석기는 만들지 않는다. 자식 프로세스는 실제 `bash 스크립트.sh`와 실제 JDK다. PHP는 이 앱이 요구하는 런타임이 아니므로 쓰지 않는다.

| 순서 | 키 | 제목(안) | 스텝 | 새로 배우는 것 |
| --- | --- | --- | --- | --- |
| A | bash-variables | Bash · 변수에 값을 담고 꺼내요 | 7 | `a=4`, `"$a"`, `=` 주변 공백 오류, 공백 값의 따옴표, 사용할 때의 따옴표(단어 분리), `unset`과 빈 값, 변수로 파일 명령 쓰기 |
| B | bash-environment | Bash · export로 자식 프로세스에 값을 전해요 | 6 | 자식 Bash는 내보내지 않은 변수를 못 본다, `export`·`printenv`, 자식이 시작될 때의 값이 복사된다, 자식의 변경은 부모로 돌아오지 않는다, `unset`·새 셸에는 남지 않는다(영구 저장 아님) |
| C | bash-command-env-args | Bash · 명령 한 번의 환경 값과 실행 인자 | 5 | `APP_MODE=dev bash show.sh`(그 명령과 자식에만), 부모 값은 그대로, `bash show.sh dev`는 환경이 아니라 `$1`, 자바 `System.getenv`와 `args` 연결 |

각 수업의 마지막 스텝은 명령을 알려 주지 않는 도전이다. 채점은 명령 문자열이 아니라 실제 결과 파일이다.

- A 도전: 고정된 두 명령 `mkdir -p "$day"`, `echo "$memo" > "$day/memo.txt"`가 주어지고 학습자가 변수 두 개를 정해 `2026-10-30/memo.txt`에 `우유 사기`가 들어가게 한다. 따옴표 없는 `memo=우유 사기`는 실제로 실패한다. 작은따옴표·백슬래시 등 같은 값을 만드는 다른 할당도 통과한다.
- B 도전: `show.sh`(받은 COLOR 기록)와 `change.sh`(받은 값을 바꿔 기록)가 `log.txt`에 줄을 덧붙인다. 학습자가 실행 순서를 스스로 정해 정확한 네 줄(내보내기 전 빈 값 → 내보낸 값 → 자식 안 변경 → 부모 값 유지)을 만든다. 먼저 export하면 첫 줄이 틀린다.
- C 도전: `greet.sh`가 `GREETING` 환경 값과 첫 인자로 인사를 기록한다. 기본 인사 → 한 번만 Hello → 다시 기본 인사의 세 줄을 만들어야 한다. `export GREETING=Hello`로 풀면 셋째 줄이 틀리고, export 뒤 `unset` 같은 동등한 풀이는 통과한다.

`a=4 echo "$a"`는 정답 예시로 쓰지 않는다. C의 해설에서 "`$APP_MODE`는 현재 셸이 먼저 펼친다"는 주의로만 말한다. 특수 내장 명령의 예외는 다루지 않는다. 비밀값 예시는 쓰지 않는다.

기존 수업과의 중복: 공백이 든 인자를 따옴표로 묶는 것은 java-arguments가 이미 다루므로 C에서 다시 가르치지 않는다. C의 자바 스텝은 java-arguments의 `args[0]`을 다시 쓰고 `System.getenv`만 더한다. 기존 수업의 바이트·버전은 바꾸지 않는다.

### 순서

전: `… java-methods, java-arguments, git-first, …` (40수업)

후: `… java-methods, java-arguments, bash-variables, bash-environment, bash-command-env-args, git-first, …` (43수업)

근거: A·B는 bash-basics만 필요하다. C의 자바 스텝은 java-launch·java-arguments가 필요하다. 세 수업은 한 흐름이라 붙여 둔다. sql-first(`-e MYSQL_PWD`)와 docker-compose-db(`environment:`)보다 앞이다. git-first의 선수는 bash-basics뿐이라 세 칸 뒤로 가도 선수 관계가 깨지지 않는다. 다른 수업의 순서를 바꿀 근거는 찾지 못해 그대로 둔다. 분류는 기존 `terminal`(터미널 · Bash·Vim), 학습 분류는 `basic`이다. 순서는 안정 ID 배열로만 바꾸며 진도는 수업 ID로 연결되므로 옮기지 않는다.

## 3. 수업별 진도 초기화

- 새 이벤트 종류 `reset`(수업 범위, 계정·코스·수업 키 그대로). 지우지 않고 더하는 기록이라 기존 합집합·대기 파일·업로드 경로를 그대로 탄다. 다른 기기·GitHub에서 늦게 온 옛 이벤트도 무효로 남는다.
- 판정 규칙(`issue_progress::effective`): 어떤 reset보다 `at`이 이른 이벤트, 또는 reset이 만들어질 때 알던 같은 초·미래 시각 이벤트(`voids` 목록)는 진도 계산에서 뺀다. 통과·완료·복습·도전·해설 열람 표시 모두 같은 규칙. 원본 기록은 그대로 남는다.
- 초기화 뒤 같은 회차에서 다시 완료하면 완료 id 끝에 마지막 reset id를 붙여 새 완료로 기록한다.
- 범위: 선택한 수업 하나, 이 계정, 이 코스. 다른 수업·다른 계정·작성한 코드 초안·실습 폴더·앱 설정은 그대로 둔다(진도만 초기화). 코스 전체 초기화는 없으므로 새로 만들지 않는다. 기존 KPC 초기화는 그대로다.
- 화면: 수업의 "학습 정보" 대화상자에 모든 학습자에게 보이는 "이 수업 진도 초기화" 버튼. 누르면 수업 이름을 넣은 짧은 확인 문장과 실제 실행 버튼·취소를 보여 준다. 자동 풀이·채점 중에는 막는다.
- 이전 앱(build ≤151)은 reset 이벤트를 읽지 못하고 건너뛰므로 옛 진도를 계속 보여 준다. 새 앱으로 업데이트하면 반영된다. 공개 대시보드도 같은 규칙으로 고친다.

## 4. 도전 과제 클리어

- 지정: 코스 `LessonRef.challenge_task`(선택 필드, 스텝 고유 코드). 수업 바이트를 다시 게시하지 않고 코스가 고정한 수업·버전·문제를 참조하는 기존 도전 과제 설계와 같다. 원본은 `tools/redesigned_courses/java/lesson-challenges.json`(수업 키별 문제 ID·근거·결정).
- 앱은 지정한 문제가 그 버전의 수업에 있고, 필수이며, 실제 채점 기준이 있을 때만 도전으로 인정한다. 아니면 무시한다(수업은 기존 완료 기준만).
- 기존 수업 지정: 마지막 문제가 실제 종합·전이 문제인 16수업(java-class-objects, java-oop-patterns, java-regex, docker 3, sql 6, h2-memory-file, java-jdbc, java-tailwind, java-react)과 새 3수업. 단순 마지막 연습인 나머지 24수업은 지정하지 않는다(통과해도 수업 클리어가 아님). 도전 과제 화면은 지정된 문제를 "수업 클리어 도전"으로, 지정되지 않은 수업은 기존처럼 "종합 문제 검토 전"으로 보여 준다.
- 판정: 초기화를 반영한 이벤트에 그 문제의 실제 채점 통과 Attempt가 있으면 도전 통과. 별도 플래그를 새로 만들지 않고 통과 기록 자체가 증거다(계정·코스·수업·버전·회차 포함). 고유 코드 문제는 기존 규칙처럼 개정 뒤에도 같은 문제로 본다. 개정으로 지정 문제가 바뀌면 새 문제를 통과해야 한다. 이전 통과 기록은 보존한다.
- 수업 클리어 = 기존 최신 버전 완료 또는 도전 통과. 게이지는 그대로(예: 2/13은 2/13). 도전만 통과한 수업은 건너뛴 문제를 통과로 만들지 않고 100%로 표시하지 않는다.
- 해설 시연·답 미리보기·실행·실패·채점 중에는 Attempt 통과가 기록되지 않는다(기존 경로). 관리자 자동 풀이도 실제 채점 결과로만 기록된다.
- 표시: 보라색 원·배경·강조 + 글자·아이콘 "◆ 도전 통과"(색만으로 구분하지 않음). 분류별·전체 순서 목록의 카드, 이어서 할 수업, 수업 안 학습 정보, 도전 과제 카드. 전부 통과한 수업은 기존 완료 표시를 유지하고 도전 표시를 함께 단다.

## 5. 출시 순서

1. 이 브랜치: 앱(reset·도전 판정·화면), 새 3수업 원본·파생물, 코스 번들(43수업, 지정 포함), 대시보드, 테스트. main으로 병합·푸시하면 MQ3 desktop release가 Windows·macOS 설치 파일을 만든다.
2. 새 수업 저장소 `jhs512/mq3-lesson-redesigned-<키>`와 버전 태그를 만들고 태그 바이트를 다시 읽어 해시를 확인한다.
3. 두 설치 파일이 있는 공개 릴리스가 새 앱 커밋을 포함하는 것을 확인한 뒤에만 코스 `course.json`을 게시한다(새 3수업 핀·순서·미리보기·도전 지정·변경 이력). 다른 핀·필드·firstJava7(java-values-7)은 원격 그대로 둔다. 게시 뒤 코스·수업 해시를 다시 읽는다.

## 6. 검증

- Rust 단위: reset 판정(부분 진도+도전, 실패는 도전 아님, 같은 회차 재완료, 늦게 온 옛 이벤트, 같은 초 이벤트, 이웃 수업·다른 계정 불변, 저장소 재개·원격 왕복), 도전 지정 검증(없는 문제·비필수·채점 없음은 무시), 개정·재배열 안정성.
- 수업: 실제 PTY Bash로 스텝마다 준비 상태 실패 → 해설대로 통과, 도전마다 오답(실패)·동등한 다른 풀이(통과), 시연 셸이 학습자 통과 증거가 되지 않음. 자바 스텝은 실제 JDK. Windows Git Bash에서 실행하고 macOS는 CI 러너의 /bin/bash 3.2로 같은 테스트를 돌린다.
- 화면: 검증 모드(가상 GitHub) 앱을 실제로 띄워 넓은·좁은 폭, 밝은·어두운 테마에서 보라색 도전 표시·초기화 확인 문장을 캡처해 본다.
- 기존 알려진 실패(java_code_guide 2건, lesson_registry 1건·ignored KPC 픽스처)는 숨기지 않고 원인을 보고한다.
