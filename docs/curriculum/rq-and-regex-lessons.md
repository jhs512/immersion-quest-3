# 요청 파싱 수업 분리 · Rq 구성안

상태: 수업 PRD·대표 문제 검토용 구성안. 실행 과정에는 아직 등록하지 않는다.
요청일: 2026-10-22

사용자 요청: 「요청을 나누고 계산의 규칙을 검증해요」를 Rq를 만드는 수업으로 발전시키고 스트림을 활용한다. 정규식은 독립 수업으로 분리한다.

## 현재 구성과 문제

`java-parser`는 요청 문자열 분해·중복 키·분리 제한 4문제와 정규식 토큰·연산 우선순위·재귀 계산기 4문제를 한 수업에 담고 있다. 요청 처리 클래스의 역할과 정규식 원리, 계산 문법을 동시에 읽게 된다.

## 분리할 수업

### 1. 정규식 · 문자열을 나누고 형식을 확인해요

목표: 구분 문자와 정규식의 차이, 전체 일치와 일부 검색의 차이를 관찰한다.

- 같은 요청 문자열 하나에서 조건 하나씩 바꾼다. 긴 새 배경을 반복하지 않는다.
- `String.split`으로 나누기 → 특수문자 `?`를 그대로 구분자로 쓰기 → `split("=", 2)`로 값 안의 등호 보존하기.
- 빈 값과 없는 값을 구별하고 분리 개수·결과 배열을 직접 확인한다.
- `[0-9]+`의 숫자 묶음 → `matches`의 전체 일치 → `find`의 부분 검색을 비교한다.
- 문자열 리터럴의 이스케이프와 정규식의 이스케이프를 한 번에 외우게 하지 않는다. 원문·실행 결과로 구별한다.
- 실전의 짧은 형식 검사까지만 다룬다. 정규식 암기, 복잡한 URL·이메일 정규식, 재귀 계산 문법은 넣지 않는다.

대표 문제: `text=a=b`를 키와 값으로 나눌 때 값 `a=b`를 보존하는 분리 방식을 고르고, 실행 후 한 줄만 수정해 비교한다.

### 2. Rq · 요청에서 명령과 값을 꺼내요

목표: 문자열 해석 책임을 Rq 객체에 모으고, 호출자는 명령·매개변수를 꺼내 쓰게 한다.

시작 계약: `update?id=2&text=hello`처럼 명령과 매개변수를 표현하는 CLI 학습용 규칙이다. 실제 HTTP 요청 파서라고 설명하지 않는다. URL 인코딩·반복 매개변수의 HTTP 의미는 후속 웹 수업에서 별도로 다룬다.

권장 선수 수업: 객체·참조, 캡슐화, Map, 예외, 스트림 기초, 정규식 기초. 추천 순서이며 진도 잠금은 아니다.

점진적 핵심 흐름:

1. 명령 하나만 있는 요청에서 `getActionName()`으로 명령을 읽는다.
2. 첫 물음표 앞뒤를 구분한다. 물음표가 없는 요청도 처리한다.
3. 하나의 `id=2`를 키와 값으로 나눈다.
4. 매개변수 두 개를 반복문으로 Map에 담고 `getParam(name)`으로 읽는다.
5. 값 안의 등호와 빈 값을 보존한다. 매개변수 없음과 빈 값을 비교한다.
6. 중복 키와 잘못된 조각을 어떻게 처리할지 명시한다. 본 구성안은 기존 요청 규칙처럼 중복 키를 거절한다. 잘못된 조각을 조용히 버리지 않는다.
7. `getIntParam(name, defaultValue)`로 숫자를 꺼낸다. 기본값은 키가 없을 때만 쓴다. 잘못된 숫자를 기본값으로 숨기지 않는다.
8. 이미 동작하는 반복문을 `Arrays.stream`으로 바꾼다.
9. `map`으로 분리하고 검증한다. 배열·중간 결과를 먼저 확인한다.
10. `Collectors.toMap`으로 모은다. 중복 키 처리와 결과를 앞의 반복문 버전과 비교한다. 중복 때 나는 예외 종류도 실제 코드와 일치시킨다.
11. 명령 분기 쪽에서는 Rq의 메서드만 호출하도록 바꾼다.
12. 입력 하나만 바꿔 정상·빈 값·중복·잘못된 숫자의 결과를 검증한다.

스트림은 Rq의 요구 사항을 이해한 뒤 같은 동작을 표현하는 수단으로 쓴다. `split → map → collect` 전체를 처음부터 긴 한 줄로 제시하지 않는다. 문제마다 판단 대상과 수정할 부분을 구체적으로 묻는다. 짧은 예측·실행·한두 줄 수정 문제를 섞고 전체 클래스를 반복 입력하게 하지 않는다.

대표 문제: `new Rq("update?id=2&text=a=b")`에서 명령·id·text를 꺼내는 결과를 확인한다. 처음에는 명령만 읽고, 다음 스텝마다 매개변수 하나와 책임 하나를 더한다.

### 3. 계산기 · 연산 순서와 괄호를 해석해요

요청 객체 수업에서 분리한다. 토큰 나누기 → 덧셈 → 곱셈 우선순위 → 괄호 → 입력을 끝까지 읽었는지 검증하는 별도 흐름으로 설계한다. 재귀가 처음 필요해지는 지점에 작은 호출 예제로 먼저 연결한다. Rq의 선수 조건으로 계산기를 요구하지 않는다.

## 검토와 전환 기준

- 각 수업 PRD와 대표 문제를 구체화해 검토한다. 이 문서를 승인된 PRD나 완성된 콘텐츠로 표시하지 않는다.
- 모든 챕터·단원·스텝에 목표와 핵심 흐름, 구체적인 할 일, 정답·해설·검사를 작성한다.
- 새 Rq·정규식·계산기 문제는 새 식별자로 만든다. 기존 `java-parser`의 문제 ID에 다른 개념을 덮어쓰지 않는다.
- 새 수업이 검증·게시된 뒤 코스에서 기존 혼합 수업을 비활성화하고 새 수업을 배치한다. 기존 풀이 이력은 보존한다.
- 정규식과 스트림 기초를 익힌 뒤 Rq를 추천하고 계산기는 독립 후속 수업으로 둔다. 주제별 묶음이 아니라 실제 선수 개념과 난이도로 순서를 정한다.
- 직접 JDK 실행으로 준비 코드·수정 코드·정답·모든 해설의 중간 실행을 검증한다. 정상 입력, 물음표 없음, 빈 값, 값 안의 등호, 중복 키, 숫자 오류를 포함한다.
- 해설은 조금 작성 → 실행 → 결과 확인을 반복하고 주의할 순간을 포함한다. 해당 미션만 해설 캐시를 갱신하고 코스 빌드를 검증한다.
