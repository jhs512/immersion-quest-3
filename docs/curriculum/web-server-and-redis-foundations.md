# 웹서버·가상 호스팅·Redis 기초 확장 계획

기준일: 2026-10-22. 상태: **계획 초안**. 사용자는 일반 웹서버, virtual hosting, 포트 기반 포워딩, `app1-127-0-0-1.nip.io` 같은 이름 기반 포워딩, Redis의 기초와 다양한 기능을 기존 자바 백엔드 과정에 녹이도록 요청했다. 이 문서는 수업 PRD 승인이나 제작·실행·게시 완료를 뜻하지 않는다.

상위 계획은 [자바 백엔드 확장 계획](java-backend-expansion.md), 후보와 의존 관계의 원본은 `tools/redesigned_courses/java/backend-extension-plan.json`이다. JPA·Kafka 등 기존 확장 범위는 유지한다. 아래 항목은 작은 수업의 후보이며, 실제 스텝 수는 개별 PRD와 대표 문제에서 확정한다.

## 1. 기존 과정에 넣는 위치

현재 게시된 자바 백엔드 과정은 24수업·233스텝이다. 여기에 아래 후보를 한꺼번에 등록하지 않는다.

| 학습 흐름 | 추가하거나 구체화할 부분 | 뒤에서 연결할 부분 |
| --- | --- | --- |
| 실행·프로세스 기초 → HTTP 요청 하나 | 웹서버의 정적 파일 제공, IP·포트·경로 | Spring Boot의 동적 응답과 비교 |
| HTTP·주소 → 웹서버 하나 | 포트 기반 가상 호스팅 → 프록시 한 홉 → 포트별 앱 분배 | 이름 기반 가상 호스팅·프록시 |
| DNS·이름 → 같은 포트의 두 사이트 | nip.io 이름 두 개, Host에 따른 선택, 기본 사이트 | 실제 배포의 도메인·HTTPS·SNI |
| 독립 Redis 서버 하나 | CLI의 키·값·만료·자료구조 | Java 클라이언트로 동일한 결과 확인 |
| Spring·SQL 기초 이후 | 캐시의 적중·누락·무효화, 세션, 요청 제한 | 트랜잭션·동시성의 실제 실패와 비교 |
| Redis 자료구조 이후 | Pub/Sub, Streams, 영속성·메모리 한도 | Kafka·운영·복구와 의미 비교 |
| 동시성·실패 모델 이후 | WATCH, Lua, 임대·소유권·분산 락의 한계 | 필요할 때 업무의 중복·재시도 처리 |

표는 범위의 묶음이며 수업을 기술별로 모두 끝내야 다음 묶음으로 가는 진도 잠금이 아니다. 실제 추천 순서는 개별 선수 경험과 난이도로 섞는다. 예를 들어 작은 Lua는 제어된 경합을 관찰한 뒤에 배치한다.

Redis 첫 수업에 Spring·JPA·DB·분산 락을 요구하지 않는다. 웹서버의 파일 제공을 배우기 위해 Spring 프로젝트를 먼저 만들게 하지 않는다. Docker를 쓸 경우 컨테이너 하나의 기초를 별도로 제공한다. Docker 설정량이 목표 개념을 가리지 않게 한다.

## 2. 반드시 구별할 말과 관찰

| 개념 | 학습자가 직접 확인할 것 |
| --- | --- |
| 웹서버 | 요청한 경로에 맞는 파일·상태·헤더를 응답한다. 첫 실습은 HTML 파일 하나다. |
| 포트로 나누기 | 주소의 포트만 바꿨을 때 연결되는 서비스나 사이트가 달라진다. |
| 가상 호스팅 | 한 웹서버가 여러 사이트 설정을 담당한다. 포트로 나누는 경우와 같은 포트에서 이름으로 나누는 경우를 각각 실험한다. |
| 리버스 프록시 | 브라우저의 요청을 받은 서버가 뒤의 앱으로 다시 요청한다. 앞 포트와 앱 포트의 로그를 함께 본다. |
| 포트 기반 프록시 | 앞의 수신 포트에 따라 다른 앱으로 전달한다. 단순히 두 앱을 다른 포트로 직접 여는 실습과 구분한다. |
| 이름 기반 프록시 | 같은 IP·같은 수신 포트에서 HTTP Host에 따라 다른 앱으로 전달한다. DNS가 앱을 골라 주는 것으로 설명하지 않는다. |
| 포트 매핑·포워딩 | 호스트 포트와 컨테이너 포트를 연결하는 경우를 뒤에서 별도로 확인한다. HTTP Host를 읽는 프록시와 같은 장치로 가르치지 않는다. 공유기 관리나 시스템 방화벽 변경은 첫 실습의 필수 행동이 아니다. |

NGINX는 수신 IP·포트로 후보를 정한 뒤 서버 이름을 비교한다. 이름이 맞지 않으면 해당 포트의 기본 서버가 선택된다. `proxy_pass`는 다른 서버로 요청을 전달한다. Docker의 포트 공개는 별도의 포트 매핑이다. 이 구별을 실제 응답과 설정으로 확인한다. [NGINX 요청 처리](https://nginx.org/en/docs/http/request_processing.html), [프록시 모듈](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass), [Docker 포트 매핑](https://docs.docker.com/engine/network/port-publishing/).

## 3. 웹서버 수업 후보: 작은 안내 사이트를 둘로 나누기

학생은 팀의 안내 사이트를 담당한다. 처음에는 안내 파일 하나만 있다. 두 번째 사이트가 필요해지고, 이후 뒤의 앱 두 개를 같은 입구로 연결한다. 단원마다 이 기본 전제를 유지하고 각 스텝에는 바뀐 조건만 짧게 보여 준다. 앱1·앱2의 응답은 서로 구별되는 고정 문구로 시작한다.

| 순서·후보 키 | 학습 목표 | 처음 할 일과 점진적 변화 | 실제 판정 근거 |
| --- | --- | --- | --- |
| W1 `web-static-first` | 파일과 HTTP 응답 연결 | 제공 사실을 알린 `index.html` 읽기 → 브라우저·curl로 보기 → 문구 한 곳 수정 → 다시 요청 | 디스크 파일과 응답 본문이 함께 바뀌는가 |
| W2 `web-path-status` | 요청 경로·상태 코드 구분 | 있는 파일 요청 → 없는 파일 요청 → 해당 파일을 직접 추가 → 같은 경로 재요청 | 경로별 본문과 200·404의 변화 |
| W3 `web-port-virtual-hosts` | 수신 포트로 사이트 구분 | 같은 웹서버의 두 사이트를 서로 다른 포트로 열기 → 포트만 바꾸어 요청 | 실제 수신 포트, 선택된 사이트, 응답 문구 |
| W4 `web-reverse-proxy-first` | 직접 요청과 중계 구분 | 앱1에 직접 요청 → 앞 서버를 거쳐 같은 앱 요청 → 앞 서버가 주는 정적 파일과 비교 | 앞 서버와 앱1의 요청 로그·본문 |
| W5 `web-port-proxy-routing` | 앞 포트와 뒤 앱 포트 대응 | 앞 포트 A → 앱1, 앞 포트 B → 앱2 → 연결 한 곳만 바꾸고 비교 | 두 앞 포트를 실제 요청해 각각 올바른 앱을 받는가 |
| W6 `dns-nipio-local` | 이름 해석과 서비스 선택 분리 | app1·app2 이름이 같은 로컬 IP로 해석됨 확인 → 같은 포트 요청 → 아직 이름별 분기가 없음을 관찰 | 두 이름의 IP와 같은 응답; DNS·HTTP 관찰을 분리 |
| W7 `web-name-virtual-hosts` | 같은 포트에서 이름으로 사이트 선택 | app1 이름 → 안내1, app2 이름 → 안내2 → 등록하지 않은 이름 요청 | Host별 문구와 기본 사이트의 응답 |
| W8 `web-name-proxy-routing` | 이름으로 실제 앱 두 개 선택 | 기존 이름별 정적 응답을 앱1·앱2의 응답으로 한 곳씩 교체 → 같은 포트에서 비교 | 실제 앱의 본문과 각각의 요청 로그 |
| W9 `web-routing-diagnosis` | 실패 위치를 구별해 수정 | 정상 연결 확인 → 이름 오타, 포트 오타, 없는 파일, 중단한 앱을 각각 별도 스텝으로 변경·복구 | 이름 해석 실패·연결 실패·404·502를 혼동하지 않는가 |
| W10 `docker-published-ports` | 호스트·컨테이너 포트 구분 | 컨테이너 하나의 기초 뒤 호스트 포트 하나만 변경 → 같은 내부 포트 요청 → 기존 주소와 비교 | 호스트의 새 포트에서 같은 응답; 웹 Host 설정은 그대로 |

W1~W9의 제안 웹서버는 NGINX다. 파일 제공 → 설정 검사·반영 → 프록시의 순서는 공식 입문 문서와 연결한다. W10은 Docker 기초 이후에 배치하며, 이름 기반 프록시의 선수 조건으로 삼지 않는다. [NGINX 입문](https://nginx.org/en/docs/beginners_guide.html).

### 이름 기반 분배의 대표 단원 초안

다음은 수업을 제작할 때 검토할 대표 문제 흐름이다. 완성된 런타임이나 승인된 스텝이 아니다.

1. 앱1·앱2를 각각 직접 요청해 서로 다른 문구를 확인한다.
2. `app1-127-0-0-1.nip.io`와 `app2-127-0-0-1.nip.io`가 같은 IP를 가리키는지 확인한다.
3. 같은 프록시 포트로 두 이름을 요청한다. 아직 이름 분배가 없으므로 같은 기본 응답을 관찰한다.
4. app1의 `server_name` 한 곳을 설정하고 반영한다. app1 요청과 미등록 이름의 요청을 비교한다.
5. app2 설정을 추가한다. 같은 IP·같은 포트에서 이름만 바꿔 두 앱을 선택한다.
6. app2의 전달 포트를 일부러 잘못 지정한다. 이름 해석은 성공하지만 앱 응답은 실패함을 확인한다.
7. 전달 포트만 수정한다. DNS 설정을 고치지 않고도 복구되는지 확인한다.
8. “두 이름이 같은 IP인데도 응답이 다른 이유는 무엇일까요?”에 답하고 실제 요청 결과와 대조한다.

주소 예시는 `http://app1-127-0-0-1.nip.io:18080/`, `http://app2-127-0-0-1.nip.io:18080/`이다. 둘의 **포트까지 같게** 두어 이름 분배를 관찰한다. 앞 서버 18080, 앱1 18081, 앱2 18082는 문서 예시다. 실제 제작에서는 실습이 소유한 사용 가능 포트를 배정하고 지시·검사에 같은 값을 넣는다. 앱1과 앱2를 처음부터 학생이 새 프레임워크로 구현하게 하지 않는다.

nip.io는 이름 안의 IP를 반환하는 DNS 서비스다. 앱 실행·프록시 설정·HTTPS 인증서를 자동으로 준비해 주는 도구가 아니다. 로컬 HTTP 실습부터 시작하고 TLS·인증서·SNI는 보안과 연결한 후속 수업에서 다룬다. `127.0.0.1`은 브라우저가 실행되는 기기 자신이며, 다른 기기에서 학생 PC를 가리키지 않는다. [nip.io 공식 설명](https://nip.io/).

공개 DNS 접근이나 로컬 주소에 대한 DNS 재바인딩 차단 여부는 준비 단계에서 확인한다. DNS를 사용할 수 없으면 먼저 `curl -H "Host: app1-127-0-0-1.nip.io" http://127.0.0.1:18080/`으로 이름 선택을 재현한다. 이것은 **HTTP Host 분배만 확인한 경로**로 기록하며 DNS·브라우저 실습까지 성공한 것으로 처리하지 않는다. 공개 DNS 응답 속도를 정답으로 삼지 않는다.

## 4. Redis 수업 후보: 값 하나에서 목적별 자료구조로

첫 단원은 독립 Redis 인스턴스 하나와 CLI다. 준비된 Java·Spring 앱은 필요 없다. 두 번째 클라이언트에서 같은 키를 읽어 프로세스 안의 지역 변수와 다름을 관찰한다. 전체 흐름은 팀 안내 서비스에서 문구를 저장하고, 만료·방문자·처리 대기·순위를 하나씩 추가하는 이야기다. 각 단원은 독립된 작은 키·값으로 시작할 수 있다.

### A. 키·값·자료구조

| 후보 키 | 해결할 작은 문제 | 개념과 핵심 명령 예 | 다음 단계로 넘어갈 관찰 |
| --- | --- | --- | --- |
| `redis-first-key` | 안내 문구 하나를 저장하고 읽기 | 접속·PING, SET, GET; 없는 키와 빈 문자열 | 클라이언트 둘이 같은 키를 읽고 값 한 곳의 변경을 확인 |
| `redis-key-lifecycle` | 안내를 바꾸고 만료시키기 | 덮어쓰기·DEL·EXISTS → EXPIRE·TTL → SET의 만료 옵션 | 기다림 전후 값 존재와 TTL 상태를 구분; 시간 경계는 허용 범위로 판정 |
| `redis-counters` | 방문 수 하나 올리기 | 숫자처럼 보이는 문자열 → INCR·DECR | 값의 갱신과 잘못된 자료형의 실패를 구분 |
| `redis-hashes` | 사용자 별명과 역할을 따로 바꾸기 | HSET·HGET·HGETALL | 필드 하나를 바꿔도 다른 필드는 유지 |
| `redis-lists` | 요청을 들어온 순서대로 꺼내기 | RPUSH·LPOP → 비어 있을 때의 대기 | 순서·빈 대기열·꺼내면 사라짐을 확인; List 자체를 재전달 보장으로 설명하지 않음 |
| `redis-sets` | 방문자를 중복 없이 세기 | SADD·SISMEMBER·SCARD → 집합 연산 | 중복 입력과 서로 다른 방문자 수의 차이 |
| `redis-sorted-sets` | 점수로 순위 매기기 | ZADD·ZINCRBY·ZRANGE | 점수 변경 전후 순위·조회 범위 비교 |
| `redis-specialized-types` | 날짜별 출석·대략적인 고유 수·가까운 점포 | Bitmaps → HyperLogLog → GEO를 독립 단원으로 분리 | 정확한 비트 판정·근사 개수·거리 조회의 서로 다른 목적 설명 |
| `redis-java-client` | CLI에서 하던 일을 Java에서도 하기 | 제공된 작은 클라이언트로 연결 → GET·SET → 결과·연결 실패 | 같은 서버·키를 CLI와 Java에서 대조; Spring은 뒤에서 연결 |

Strings·Hashes·Lists·Sets·Sorted sets·Streams 등은 서로 다른 자료 모델이다. 처음부터 명령 사전을 외우게 하지 않고, 필요한 질문에 맞는 구조를 고른 뒤 실제 상태를 확인한다. 기능 범위와 명령은 제작할 Redis 서버 버전에 고정한다. [자료형 개요](https://redis.io/docs/latest/develop/data-types/), [자료형 비교](https://redis.io/docs/latest/develop/data-types/compare-data-types/).

### B. 이미 배운 자료구조를 실제 사용에 연결

| 후보 키 | 정상 예제 → 조건 하나 변경 | 확인할 원리·한계 |
| --- | --- | --- |
| `redis-cache-atomicity` | 가짜 원본 조회 한 번 → 캐시 적중 → 원본만 변경 → 캐시 무효화 → 다시 읽기 | 캐시와 원본의 불일치, TTL만으로 즉시 일치하지 않음; DB는 나중에 교체 |
| `redis-session-state` | 로그인 상태 하나 저장 → 다른 앱 인스턴스에서 조회 → 만료 | 서버 상태 공유와 만료; 인증 자체는 보안 기초 뒤 연결, 실습용 가짜 토큰 사용 |
| `redis-rate-limit` | 한 사용자 요청 수 기록 → 제한에 닿음 → 기간 변경 | 카운터와 만료를 따로 호출할 때의 실패를 먼저 경험하고 뒤의 Lua와 연결 |
| `redis-transactions-scripts` | 두 클라이언트의 읽기·쓰기 → WATCH 충돌 → MULTI/EXEC → 짧은 Lua | 한 번의 명령·여러 명령·조건부 갱신의 범위를 구별; SQL 롤백과 같다고 설명하지 않음 |
| `redis-pipelining` | 독립 명령을 개별 요청 → 묶어서 전송 | 왕복을 줄이는 것과 원자성의 차이; 임의의 성능 수치를 정답으로 고정하지 않음 |

세션 수업의 도입은 단순 상태 공유다. 실제 로그인 연동은 Spring·세션/쿠키·인증을 배운 뒤 진행한다. 요청 제한은 작은 고정 구간부터 시작하고 경계의 한계를 확인한 뒤 필요할 때 더 정교한 방식을 비교한다. 분산 락은 이 표의 첫 활용 예제로 넣지 않는다.

### C. 전달·저장·운영의 서로 다른 보장

| 후보 키 | 최소 실험 | 관찰과 후속 연결 |
| --- | --- | --- |
| `redis-pubsub` | 구독자 하나와 메시지 하나 → 구독을 끊은 동안 발행 → 재접속 | 접속 중 전달과 유실; 이전 발행을 다시 읽는 로그로 취급하지 않음 |
| `redis-streams` | XADD·XRANGE·XREAD → 그룹 → ACK·미확인 목록·다른 소비자의 회수 | 남아 있는 메시지와 확인 상태, 재전달·중복 처리; Kafka와는 배운 뒤 비교 |
| `redis-persistence` | 키 하나 → 저장 설정을 고정한 정상 재시작 → 별도의 비정상 종료 | RDB와 AOF의 복구 범위, 저장 주기·fsync 설정의 차이; 항상 전부 보존된다고 가르치지 않음 |
| `redis-memory-eviction` | TTL로 만료 → 별도 실험에서 작은 메모리 한도 도달 | 시간 만료·정책에 따른 퇴거·쓰기 거절의 차이; 테스트 인스턴스만 사용 |
| `redis-replication-basics` | 정상 복제 → 복제본 중단 → 복구·지연 관찰 | 복제와 백업·장애 전환은 다른 개념; Sentinel·Cluster는 선택 심화로 분리 |

세부 근거와 전달·원자성·영속성의 경계는 [Redis 공식 문서 조사](redis-foundations-research-2026-10-22.md)에 보관한다. JSON·Search·확률 자료구조·시간 자료·벡터 등 추가 기능은 해당 버전과 실행 환경에서 지원됨을 확인한 뒤 선택 후보로 다룬다. 최신 문서에 나온 기능을 첫 수업의 필수 설치나 기초 선수 지식으로 자동 추가하지 않는다.

## 5. 수업을 실제로 만드는 기준

- 수업·챕터·단원·스텝 각각의 교육 목표를 사용자에게 보인다. 내부 핵심 흐름에는 시작 상태·새 개념·바꿀 한 곳·실제 관찰·완료 기준을 기록한다.
- 각 단원은 하나의 상황으로 이어진다. 앞 스텝에서 이미 안 배경을 반복하지 않고 새 조건만 짧게 쓴다. 독립 준비 상태로 시작하는 경우는 먼저 알린다.
- “기준을 비교해요” 같은 활동명으로 선택지를 내지 않는다. “같은 IP·포트인데 앱이 다른 이유는 무엇일까요?”, “같은 방문자를 두 번 추가하면 고유 방문자는 몇 명일까요?”처럼 답할 대상을 질문한다.
- 명령을 따라 쓴 기록만으로 통과시키지 않는다. 실제 HTTP 응답·선택된 서버·로그, Redis 자료형·키·TTL·메시지 확인 상태를 검증한다. 개념상 명령 자체가 목표일 때만 명령 기록도 판정에 사용한다.
- 예측 선택 → 실제 실행 → 예상과 결과 비교를 필요할 때 넣는다. 작은 설정·코드 수정과 실행을 섞고, 모든 문제를 선택형으로 통일하지 않는다.
- 시각화는 브라우저 → 웹서버 → 앱 경로, 키·만료·자료구조, 소비자의 확인 위치를 이해하는 데 필요할 때 사용한다. 글과 조작을 복잡하게 늘리지 않는다. 신규 교수법을 채택한 것으로 취급하지 않는다.
- 해설은 별도 소유 폴더·프로세스·서버·키 공간에서 시연한다. 종료하면 학생의 파일·입력·실습 상태로 돌아온다. 실제 명령 한 번 뒤 결과를 짚고 다음으로 넘어간다.
- 같은 단원은 상태를 이어 쓰되, 초기화는 정해진 시작 상태를 정확히 복원한다. 수업 밖의 Redis·서버·프로세스를 종료하거나 개인 데이터를 지우지 않는다. 공유 인스턴스에 FLUSHALL/FLUSHDB를 실행하지 않는다.

## 6. 제작 전 환경·검증 조건

1. Windows·Apple Silicon·Intel Mac에서 동일한 핵심 실험을 수행할 방법을 정한다. 실제 NGINX·Redis의 버전·설정·실행 상태·정리 범위를 기록한다. 브라우저 흉내나 Java Map을 실제 Redis 실행으로 표시하지 않는다.
2. 각 수업은 자신이 소유한 로컬 작업 폴더와 프로세스를 사용한다. 시스템 웹서버·서비스 설정과 hosts 파일을 처음부터 수정하게 하지 않는다. 설정 파일은 작업 폴더에 두고 읽기·검사·reload를 실제 수행한다.
3. 기본 실습은 권한이 필요 없는 포트와 로컬 접속으로 시작한다. 포트 충돌·실행 경로·필요한 다운로드·DNS 접근을 준비 진단에서 보여 준다. 컨테이너 안의 localhost와 호스트의 localhost는 네트워크 공간이 다름을 연결 시점에 설명한다.
4. TTL은 실행 지연을 허용하는 범위로 판정한다. 소비자·경합은 연결 준비나 명시적 동기화로 순서를 제어한다. sleep이나 인터넷 지연의 우연을 정답으로 삼지 않는다.
5. 영속성·복제 실험은 고정한 정책에서 보장되는 범위를 검사한다. 장애·유실 가능성을 보여 주는 사례를 매 실행마다 반드시 같은 개수가 유실되는 시험으로 만들지 않는다.
6. 정답·오답·반례, 해설 전후 보존, 재진입·초기화, 다른 코스·학생 상태와의 분리를 검증한 수업만 과정에 추가한다. 계획 파일의 추가만으로 현재 코스가 늘어난 것으로 표시하지 않는다.

## 7. 다음 제작 단위

이미 남아 있는 `bash-environment` 등 실행 기초의 제작 순서는 유지한다. 새 요청의 첫 제작 후보는 **W1: 파일 하나를 실제 웹서버로 제공하기**다. 이 수업의 PRD·대표 문제에서는 파일 수정과 HTTP 응답이 연결되는 최소 경험만 확인한다. Redis의 첫 제작 후보는 별도로 **`redis-first-key`**이며, 웹서버·Spring 수업 전체를 마쳐야 열리는 과정으로 만들지 않는다.

두 후보의 PRD·대표 문제 검토 → 작은 수업 제작 → 실제 런타임·해설·초기화 검증 → 단계적 등록 순서로 진행한다. 이번 요청에서는 이 계획과 기존 계획의 연결만 작성한다.
