# 수업 풀이 기록 초기화·코스 전체 흐름 문서 계획

기준일: 2026-10-22. 상태: **기획**. 웹서버·Redis 확장 계획을 논의하던 중 사용자가 다음 기능을 추가 요청했다. 이 문서는 현재 동작 조사를 반영한 후속 기능 설계이며, UI나 저장 방식이 이미 변경됐다는 뜻이 아니다.

1. 특정 수업의 풀이 기록을 초기화한다.
2. 코스에서 버튼을 누르면 내부 수업별 스토리를 하나의 문서로 읽는다.

## 1. 특정 수업의 풀이 기록 초기화

### 사용자 동작과 범위

- 코스의 수업 카드에서 보조 메뉴로 **풀이 기록 초기화**를 제공한다. 기존 문제의 **초기화** 버튼과 구분한다.
- 실행 전 현재 코스명·수업명·초기화 범위를 확인한다. 취소가 기본이며, 초기화 중에는 중복 실행을 막는다.
- 범위는 **현재 GitHub 사용자 ID + 현재 코스 ID + 선택한 수업 ID**다. 사용자 이름을 바꿔도 범위는 바뀌지 않는다. 다른 코스에서 같은 수업을 학습한 기록은 유지한다.
- 선택한 범위의 성공·오답 시도·완료·복습·해설 열람 기록이 새 학습의 집계에 들어가지 않도록 한다. 학생이 저장한 답안·선택·최근 문제 위치도 새 학습 기준으로 비운다. 확인 창에 이 범위를 명시한다.
- 코스별 이름, 다른 수업의 기록, 다른 사용자의 기록, 코스·수업 콘텐츠는 유지한다.
- 실제 Git 저장소·PR·파일·외부 서비스의 상태를 지우는 기능으로 사용하지 않는다. 특히 실제 GitHub PR 수업에서 풀이 기록 초기화를 저장소 재생성·PR 삭제로 연결하지 않는다. 실습 재시작 제한은 따로 안내한다.

### 현재 구조와 필요한 변경

현재 `ProgressKey`는 사용자·코스·수업을 구분한다. 진행 이력은 로컬 `ProgressStore`와 GitHub 이슈의 추가형 이벤트를 합친다. 수업 전체에 대해 이 범위를 초기화하는 공개 플레이어 기능은 없다. 오래된 기본 과정용 코스 초기화 함수는 이 기능에 그대로 재사용하지 않는다.

단순히 SQLite나 화면의 진도만 지우면 동기화 후 옛 성공 기록이 되살아날 수 있다. 다음 제작에서는 **학습 기록의 초기화 세대**를 도입하는 방안을 우선 검토한다.

- 기존 이벤트는 기본 세대의 기록으로 읽는다. 초기화는 새 세대를 시작하는 별도 이벤트로 남긴다. 과거 이슈 댓글을 삭제하는 방식에 의존하지 않는다.
- 새 시도·완료·해설·답안은 해당 세대를 명시한다. 현재 진도는 활성 세대의 기록으로 계산한다. 옛 데이터의 다운로드·재시도·중복 전송이 완료 상태를 되살리지 않아야 한다.
- 같은 초의 이벤트를 시간만 비교해 앞뒤로 나누지 않는다. 오프라인 재접속·기기 둘의 동시 초기화·초기화 직전 업로드 중인 기록의 충돌 규칙을 구현 전에 확정한다. 관측한 세대의 순서와 고유 초기화 ID로 합쳐도 동일한 결과가 나는지 확인한다.
- 새 세대를 모르는 열린 수업에서 옛 답을 제출하면 초기화 뒤 기록에 잘못 합쳐지지 않게 한다. 새 학습 상태를 다시 열도록 처리한다.
- 기록 저장·대기열 반영은 로컬 트랜잭션으로 함께 수행한다. 로컬 화면은 즉시 0%가 되고, 외부 반영 중·실패·재시도 상태를 구분한다.
- GitHub 전송은 기존의 최대 5분 간격 배치와 종료 시 반영 정책을 따른다. 초기화가 무제한 즉시 이슈 전송을 일으키는 우회로가 되어서는 안 된다.
- 관리자 대시보드·이슈 요약·코스 카드·문제 완료 표시·해설 열람 표시가 같은 세대를 기준으로 집계해야 한다. 외부 화면의 지연을 로컬 초기화 실패로 잘못 표시하지 않는다.

### 완료 판정

1. 코스 A와 B에 같은 수업을 넣고 둘 다 푼 뒤 A만 초기화한다. A는 0%, B는 이전 진도를 유지한다.
2. 같은 코스의 다른 수업·다른 계정의 기록과 이름은 바뀌지 않는다.
3. 초기화 → 앱 재시작 → 오래된 원격 기록 재수신 → 동기화를 거쳐도 완료가 되살아나지 않는다.
4. 초기화 직전의 전송 실패·대기 기록을 재시도해도 새 학습에 합쳐지지 않는다.
5. 같은 초의 초기화·새 제출, 오프라인 새 기기, 기기 둘의 충돌을 결정적인 사례로 검사한다.
6. 새 학습은 정상적으로 다시 통과·완료되고 대시보드에도 같은 진도가 반영된다.
7. 실제 학생 파일·GitHub 저장소·PR이 보존되고 취소·중복 클릭·오류 복구가 동작한다.

## 2. 코스 전체 흐름 문서

### 버튼과 문서 형태

- 코스 수업 목록 상단에 **코스 전체 흐름** 버튼을 제공한다. 문제 화면의 좁은 상단 도구 모음에 상시 버튼을 더하지 않는다.
- 플레이어 안에서 넓은 문서 보기로 연다. 기존 학습 상태를 유지하며 닫으면 같은 위치로 돌아온다. 외부 프로그램을 실행하지 않는다.
- 여러 수업을 클릭해 보지 않아도 **문서 하나**에서 읽을 수 있게 한다. 문서 안의 목차로 수업 위치에 이동할 수 있다.
- 기본 내용은 코스 소개 → 추천 순서 → 수업별 목표·시작 상황·이야기의 변화·도달할 이해다. 큰 흐름을 보는 문서이므로 모든 문제·명령·해설을 펼쳐 붙이지 않는다.

### 실제 데이터와 콘텐츠의 경계

현재 설치된 `CourseManifest`의 순서와 각 수업의 `description`, `objectives`, 챕터·단원의 `premise`를 우선 사용한다. 작성자가 보관하는 PRD와 `core_flow`는 내부 제작 자료이며 학습자 문서의 원문으로 내보내지 않는다. 문제의 정답 코드·정답 선택지·교사용 시연도 포함하지 않는다.

예를 들어 브랜치 수업은 “팀의 안내문 담당 → 외부 파일 가져오기 → feature에서 첫 기능 → main에 반영 → feature2에서 다음 기능 → 다시 반영”의 이야기로 보여 준다. 어떤 커밋·명령을 입력해야 하는지까지 정답으로 제공하지 않는다.

단원 전제만으로 이야기를 읽기 어려운 수업은 후속 제작에서 학생용 **수업 이야기 요약**을 작성한다. 후보 필드는 역할·시작 상황·진행 중의 변화·도착점·다음 수업과의 연결이다. 원본 목표·핵심 흐름이 바뀌면 인접 레이어 검토에 따라 요약을 갱신한다. 다음 사항을 지킨다.

- 모든 수업을 억지로 하나의 앱 개발 스토리로 묶지 않는다. 독립 예제로 원리를 배우는 구간과 프로젝트 적용 구간을 구분해서 설명한다.
- 없는 수업이나 미제작 JPA·Kafka·Redis 후보를 학습 가능한 수업처럼 보여 주지 않는다. 작성된 장기 계획은 원한다면 별도 “확장 예정” 영역에서 분명히 구분한다.
- 한 번 열 때마다 LLM으로 새 이야기를 만들지 않는다. 검토한 원본을 사용하고 코스·수업의 콘텐츠 해시를 기준으로 재생성한다.
- 사용자가 현재 볼 수 있는 코스·수업 범위를 지킨다. 다른 관리자 계정의 전체 수업이나 다른 버전의 이야기가 섞이지 않게 한다.
- 코스 업데이트 뒤에는 새 순서와 새 요약으로 바뀐다. 열람 자체는 문제 통과·수업 완료·해설 열람으로 기록하지 않는다.
- 설치된 수업 자료로 오프라인에서도 읽는다. 자료가 없거나 준비되지 않은 수업은 그 사실을 표시하고 임의의 스토리를 만들어 채우지 않는다.

### 완료 판정

1. 코스 버튼 한 번으로 여러 수업의 흐름을 하나의 문서에서 볼 수 있다.
2. 실제 코스 순서·수업 제목·단원 상황과 문서가 일치한다. 같은 수업을 사용하는 다른 코스의 순서는 독립적으로 반영한다.
3. 콘텐츠 업데이트·수업 추가·제외·순서 변경 시 문서도 해당 버전을 따른다.
4. 내부 PRD·핵심 흐름·정답·학생 개인 답안·다른 사용자의 진도가 노출되지 않는다.
5. 키보드·문서 스크롤·목차·닫기가 동작하고, 닫은 뒤 원래 학습 상태를 보존한다.
6. 흐름 문서를 읽어도 풀이 기록이 바뀌지 않는다.

## 3. 제작 순서

1. 초기화의 데이터 범위·세대·동기화 계약과 UI 확인 문구를 스펙으로 확정한다.
2. 진도 집계·저장·동기화·대시보드에서 초기화의 유지와 코스 간 분리를 먼저 검증한다.
3. 수업 카드의 초기화 UI와 새 학습 재진입을 연결한다.
4. 설치된 코스·수업 원본에서 전체 흐름 문서를 구성하고 코스 버튼을 연결한다.
5. 실제 플레이어에서 두 기능의 상태 보존·오프라인·오류·업데이트 경로를 확인한다.

현재 단계에서는 위 기능을 계획으로 기록했다. 초기화 실행이나 GitHub 이슈·학생 진도 변경은 하지 않았다.
