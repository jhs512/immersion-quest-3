# 자바 백엔드 확장 계획

기준일: 2026-10-20. **가장 단순한 상태에서 시작하고, 새 개념을 하나씩만 더한다.** 목적은 기술을 많이 설치하거나 긴 코드를 완성하는 것이 아니라, 결과가 왜 바뀌는지 이해하는 것이다.

현재 과정은 20수업 187스텝이다. 아래는 후속 확장의 검토용 계획이다. 계획된 기술이 이미 앱 수업으로 제공된다고 표시하지 않는다. 기존 문제 코드·완료 기록은 유지한다.

## 난도 상승을 확인하는 기준

각 스텝의 제작 표에는 다음 다섯 가지를 적는다.

1. 이미 해 본 경험은 무엇인가?
2. 이번에 새로 배우는 개념 하나는 무엇인가?
3. 바꾸는 값·조건·동작 하나는 무엇인가?
4. 어느 출력·파일·응답·상태를 보면 차이를 알 수 있는가?
5. 이 결과를 설명하지 못한다면 어떤 더 작은 스텝으로 나눌 것인가?

첫 실행 예제는 Main.java 하나, 메모 한 줄, 외부 라이브러리와 서버 없이 시작한다. 학생이 고치는 부분은 보통 1~3줄이다. 첫 Spring 예제에는 DB가 없고, 첫 SQL 예제에는 웹 서버가 없다. 처음 컨테이너를 실행할 때 앱·DB·Redis·Kafka를 함께 올리지 않는다. 새 외부 서비스는 한 단원에 하나씩 도입한다.

파일 수나 시스템 수를 늘리기 전에 같은 예제에서 정상 결과를 확인한다. 조건 하나를 바꾼 뒤 차이를 읽고, 수정해서 다시 확인한다. 설정 오류·문법 오류·동시성 오류를 한 문제에 섞지 않는다. 실패 원인이 여럿이면 예제를 더 나눈다.

이 기준은 `docs/content-rules.md`의 공통 정책에 반영했다. 학습자의 수업 선택을 막는 진도 잠금이 아니라 작성자의 제작·검토 기준이다.

## 전체 흐름

큰 이야기의 중심은 작은 메모 앱이다. 문구 출력 → 파일 저장 → HTTP 조회 → DB 저장 → 사용자별 접근 → 조회수·중복 요청 → 생성 알림 → 실시간 알림 → AI 요약으로 커진다. 단원 안에서는 같은 상황을 이어 쓴다. 다른 주제에 작은 별도 실험이 더 쉬우면 실험의 시작 상태를 명시한다.

| 순서 | 수업 묶음 | 처음에는 이것만 | 그다음 하나씩 더할 것 |
| --- | --- | --- | --- |
| 0 | 현재 기초 과정 | 파일·Git·자바 값과 객체 | 컬렉션·스트림·파일·작은 CRUD·검사 |
| 1 | 실행·설정·빌드 | 파일 하나와 출력 한 줄 | 컴파일, 실행 인수, 변수의 범위, 백그라운드, Gradle, JVM 옵션 |
| 2 | HTTP와 네트워크 | 로컬 GET 요청 하나 | 응답·상태 코드, IP·포트, DNS, JSON, REST, 연결 실패·제한시간 |
| 3 | DI와 Spring Boot | 생성자로 객체 하나 전달 | 수동 조립과 DI 컨테이너 비교, 작은 Boot 앱, 검증·오류 응답, 필터 한 개 |

추천 순서다. 전체 후보 수업을 한 번에 필수 등록하거나 제작 완료로 표시하지 않는다. 각 묶음도 여러 작은 수업으로 나눈다. 현재 React·Tailwind 수업은 유지하고 후속 확장에서는 화면 이해를 위한 보조 학습으로 위치를 검토한다.

## 묶음을 나누는 구체적인 방법

### 1. 실행·설정·빌드

첫 수업에는 **컴파일과 실행만** 넣는다. 그 뒤 다음을 별도 수업으로 진행한다.

- 소스 파일 실행 → class 만들기 → class 실행 → 소스만 수정했을 때의 차이.
- 프로그램의 실행 인수 하나 → JVM 시스템 속성 하나. 둘을 처음부터 함께 전달하지 않는다.
- 셸 변수 → 자식 프로세스에서 안 보이는 경우 → export한 환경변수 → 명령 한 번에만 전달하는 환경변수.
- 앞에서 실행해 종료 기다리기 → 뒤에서 실행하기 → 자기 작업의 PID·로그·종료 상태 확인.
- 수동 javac·java로 해 본 일을 Gradle의 작업과 비교한다. Wrapper로 실행 버전을 고정하고, 의존성 하나·테스트 하나를 추가한다.
- 빌드 도구 옵션, 컴파일 옵션, JVM 옵션, 앱 인수를 분리한다. `-D`의 위치를 바꾸는 예제와 작은 힙 한도를 확인한 뒤에야 고급 튜닝을 고려한다.

‘임시변수’는 모호하게 한 단어로 부르지 않는다. 자바 지역 변수, export하지 않은 셸 변수, 명령 한 번의 환경변수, 세션에서 export한 환경변수를 각각 구분한다. export했다고 시스템에 영구 저장되는 것처럼 가르치지 않는다. `.env` 파일도 프로그램이 읽어야 적용된다고 설명한다.

### 2. 네트워크와 HTTP

먼저 로컬 주소로 요청해 본문 한 줄을 받는다. 다음에 경로 하나, 상태 코드 하나, JSON 필드 하나를 더한다. IP는 대상 주소, 포트는 대상 서비스, DNS는 이름 해석이라는 역할을 나눠 확인한다. `localhost`가 언제나 외부 DNS 질의를 뜻한다고 설명하지 않는다.

GET으로 메모 하나 읽기 → 없는 번호 처리 → POST로 한 개 만들기 → 잘못된 입력 처리 → 수정·삭제 → 페이지 단위 조회 순서다. HTTP·DNS·연결 실패를 구별하고 제한시간을 둔다. 실습 응답은 로컬에서 재현하며 공개 도메인의 IP나 인터넷 응답 시간을 정답으로 고정하지 않는다.

### 3. DI와 Spring Boot

기존 역할·인터페이스·CRUD 수업을 재사용해 저장소 객체 하나를 서비스 생성자에 직접 전달한다. 그 조립 역할을 Spring에 넘겨 같은 결과인지 비교한다. 애너테이션 목록부터 외우게 하지 않는다.

첫 Boot 앱은 조회 응답 하나만 낸다. 서비스 분리는 새 역할이 필요해질 때 한 파일씩 추가한다. 요청 검증·DTO·오류 응답도 한 번에 하나씩 넣는다. 요청 흐름을 볼 수 있는 필터 한 개를 먼저 관찰하고, 보안 단계에서 Security 필터 체인과 연결한다.

### 4. SQL·DB와 컨테이너

SQL 의미를 익힐 때는 표 하나·두 행·SELECT 하나로 시작한다. WHERE → INSERT → UPDATE → DELETE → 제약 → 조인 → 인덱스·실행 계획을 작은 데이터로 추가한다.

메모리/파일은 저장 방식이고, SQLite/PostgreSQL/MySQL은 다른 DB라는 점을 구분한다. SQLite의 결과를 PostgreSQL이나 MySQL의 결과라고 표시하지 않는다. PostgreSQL 문법을 가볍게 다루는 후보는 PGlite지만, 단일 연결인 이 환경을 다중 연결의 락·격리 실험에 사용하지 않는다. 그런 실험은 실제 PostgreSQL/MySQL에서 수행한다. [PGlite의 메모리·파일 저장 및 연결 범위](https://pglite.dev/docs/)

Docker는 독립된 컨테이너 하나를 실행하고 멈추는 경험부터 시작한다. 그 다음 PostgreSQL 하나, 연결 하나를 추가한다. JDBC의 연결·파라미터 쿼리·닫기를 확인한 뒤 연결 풀을 소개한다. MySQL은 공통 SQL을 전부 반복하지 않고 SQL 문법·제약·격리 등의 차이를 관찰하는 수업으로 둔다. 실제 서버 검사에는 해당 엔진을 사용한다.

### 5. 트랜잭션·롤백·JPA

메모 저장 하나가 성공하는 것을 먼저 본다. 기록 저장을 하나 추가한 뒤 두 번째 동작이 실패하는 조건만 만든다. 그 다음 BEGIN·COMMIT·ROLLBACK을 한 개씩 도입한다. [PostgreSQL 트랜잭션 튜토리얼](https://www.postgresql.org/docs/current/tutorial-transactions.html)

SQL과 JDBC에서 이해한 뒤 JPA의 매핑 → 저장 → 조회 → 수정 → flush를 관찰한다. 실행 SQL을 같이 보여 준다. `@Transactional`은 무조건 모든 실패를 되돌린다고 가르치지 않는다. 프록시 경계·예외 종류·롤백 규칙은 정상 사례를 이해한 뒤 각각 짧은 반례로 나눈다. N+1과 지연 조회는 데이터와 관계를 조금 늘렸을 때 쿼리 수가 어떻게 바뀌는지로 이해한다. [JPA의 트랜잭션 경계](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html)

### 6. 해시와 암호·시큐리티

hashCode·해시 테이블 조회 → 내용 지문·변경 확인·ETag·중복 판별 → 암호학적 해시를 구분한다. 해시 값이 같으면 항상 내용도 같다고 가르치지 않는다.

비밀번호는 복호화해서 대조하지 않는다. 검증된 적응형 비밀번호 인코더로 생성·검증을 경험하고, 단순 SHA-256 저장과 구별한다. 이후 HMAC, 인증된 대칭키 암호화, 공개키·개인키와 서명 검증을 한 실험씩 다룬다. 암호 알고리즘을 직접 만드는 수업으로 만들지 않는다. [Spring Security 비밀번호 저장](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)

보안은 메모 하나·사용자 하나에서 시작한다. 로그인 여부와 소유자 권한을 구분하고 세션·쿠키, CSRF, CORS, 필터 흐름을 나눠 확인한다. JWT·OAuth를 첫 로그인 예제의 필수 설정으로 섞지 않는다. 비밀값의 전달·로그 노출·권한은 해당 예제에서 필요할 때 구체적으로 확인한다.

### 7. 동시성은 해결해야 하는 문제별로

첫 예제는 프로세스 하나, 공유 숫자 하나, 작업 둘이다. 단순한 sleep 타이밍이나 우연한 출력 순서로 정답을 정하지 않는다. 제어된 순서로 두 읽기·두 쓰기가 겹치는 작은 상태표를 먼저 확인한다.

| 해결하려는 문제 | 비교할 방법 | 같이 확인할 한계 |
| --- | --- | --- |
| 공유 자체를 줄이기 | 불변 데이터·작업별 데이터·단일 소유자 | 결과 합치기·처리량 |
| 같은 JVM에서 묶어서 바꾸기 | synchronized·ReentrantLock | 다른 프로세스는 보호하지 않음 |
| 값 하나 갱신하기 | Atomic·CAS | 여러 값의 업무 규칙 전체를 자동 보장하지 않음 |
| 공유 컬렉션 다루기 | ConcurrentHashMap의 원자 연산 | 여러 호출 조합은 별도 문제 |
| 동시에 실행할 작업 수 제한 | Semaphore·실행기·대기열 | 원자적 상태 갱신과 다른 목적 |
| DB의 숫자 갱신 | 원자 UPDATE·조건부 UPDATE | 영향받은 행 수·실패 처리 |
| 같은 행의 충돌 처리 | 낙관적 락·비관적 락 | 재시도·대기·데드락 |
| 같은 요청의 중복 처리 | 유일 제약·멱등 키 | 요청 신원과 보관 범위 |
| Redis의 값 갱신·캐시 | 원자 명령·작은 Lua·TTL | 영속성·무효화·다중 인스턴스 범위 |
| 여러 프로세스의 소유권 | 임대 기반 분산 락·소유자 확인·fencing | 만료·중단·오래된 작업자·저장소의 강제 검증 |
| 순서대로 업무 처리 | 단일 소비자·Kafka의 같은 키 파티션 | 재전달·중복·파티션 밖의 순서 |

스레드 풀·Future·CompletableFuture·가상 스레드는 실행을 조직하는 수단으로 다룬다. 가상 스레드를 쓴다고 공유 상태의 경합이 없어지는 것으로 설명하지 않는다. Redis 캐시에서 값을 읽고 만료시키는 실습을 한 뒤 분산 락으로 간다. 락 TTL 안에 작업이 끝날 것이라고만 가정하지 않는다. [가상 스레드](https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html), [Redis 분산 락과 fencing의 주의점](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

### 8. Spring 이벤트·Kafka·Streams

같은 프로세스의 메서드 호출 → Spring 동기 이벤트 → 커밋 뒤 이벤트 → 비동기 실패 → 저장됐지만 알림이 사라지는 경우 순서로 진행한다. AFTER_COMMIT이 메시지를 영구 보관하는 장치인 것처럼 설명하지 않는다. 이 필요를 이해한 뒤 outbox와 Kafka를 추가한다. [트랜잭션 이벤트](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)

Kafka는 메시지 한 개·토픽 하나에서 시작한다. 키·파티션·오프셋·소비자 그룹·중복 재전달·재시도·격리 처리를 각각 다룬다. DB와 외부 부수 효과까지 무조건 정확히 한 번 처리된다고 주장하지 않는다.

Kafka Streams는 Java Stream과 이름이 비슷하지만 입력의 지속성·상태·시간이 다름을 비교한다. 변환 하나 → 키별 합계 → 시간창 → 늦은 이벤트로 확장한다. 로컬 토폴로지 검사와 실제 브로커 검사를 분리한다.

### 9. SSE·WebSocket·STOMP

서버 알림 한 줄을 받는 SSE부터 시작한다. 다음에 재연결·마지막 이벤트를 확인한다. 이어 WebSocket에서 보낸 글 한 줄을 돌려받고, STOMP의 목적지·구독을 추가한다. STOMP를 별도 연결 전송 기술로 혼동하지 않는다. 연결 인증과 각 메시지의 권한도 단계적으로 나눈다. [Spring STOMP](https://docs.spring.io/spring-framework/reference/web/websocket/stomp.html)

### 10. 로컬 AI·Spring AI

먼저 고정 응답을 내는 가짜 요약기로 요청·실패·제한시간을 이해한다. 그 후 로컬 모델 하나로 같은 계약을 교체한다. Mac에서는 네이티브 Ollama를 우선 후보로 두고, Windows는 실제 장치와 가속 환경을 확인한다. vLLM은 하드웨어와 해당 플러그인 지원을 확인한 선택 실습으로 둔다. 현재 공식 문서는 Apple Silicon 플러그인 경로도 소개하므로 ‘무조건 Linux GPU 전용’으로 단정하지 않는다. [Ollama 환경 안내](https://docs.ollama.com/faq), [vLLM 설치·하드웨어](https://docs.vllm.ai/en/latest/getting_started/installation/)

Spring AI를 붙인 뒤 구조화 결과 하나 → 실패 처리 → 스트리밍 → 아주 작은 평가 자료 → 검색 보조를 추가한다. 첫 수업에 벡터 DB·RAG·에이전트·도구 호출을 한꺼번에 넣지 않는다. ‘답이 그럴듯함’ 대신 준비한 작은 질문·사실·실패 사례로 전후를 비교한다. [Spring AI ChatClient](https://docs.spring.io/spring-ai/reference/api/chatclient.html)

### 11. 운영·검사와 복구

학습 중 사용한 기능을 필요할 때 묶는다. 앱+DB로 Compose를 시작하고 Redis·Kafka는 해당 기능을 익힌 뒤 추가한다. 요청 ID와 로그 → 상태 확인 → 메트릭 → 제한시간·재시도 → 재시작·백업/복원을 나눈다. Testcontainers는 실제 DB 통합 검사가 필요한 시점에 소개한다. Kubernetes와 다중 마이크로서비스는 현재 첫 확장의 필수 범위가 아니다.

## 먼저 착수한 1차 초안

첫 신규 수업의 추천 위치는 기존 `java-crud` 뒤, `java-testing` 앞이다. 작은 앱은 이미 이해했고, 테스트와 Gradle을 확장하기 전에 소스·산출물·실행의 차이를 직접 확인할 수 있는 위치다. 기존 수업의 완료 기록이나 식별자는 바꾸지 않는다.

제목: **자바 · 파일 하나를 실행하고 다시 빌드해요**

| 스텝 | 행동 | 이번에 비교할 것 |
| --- | --- | --- |
| 1 | 제공한 Main.java 읽기 | 출력할 문구가 어디 있는가 |
| 2 | java Main.java | 소스 파일 실행의 출력 |
| 3 | 문구 한 곳 수정 후 같은 명령 | 수정 전후 출력 |
| 4 | javac Main.java, 익숙한 ls | 출력과 class 파일 생성의 차이 |
| 5 | java Main | 이미 만든 클래스 실행 |
| 6 | 소스만 수정하고 java Main | 소스와 기존 산출물의 차이 |
| 7 | 다시 javac Main.java | 산출물 갱신 |
| 8 | java Main | 갱신 뒤 출력 |

대표 문제는 스텝 6이다. 소스에 ‘셋째 메모’를 적은 뒤 기존 클래스를 실행하면 어떤 문구가 나오는지 먼저 고르고 비교한다. 정답 근거는 실제 JDK 출력과 class 파일의 전후 상태다. [Java 실행 모드](https://docs.oracle.com/en/java/javase/25/docs/specs/man/java.html), [javac의 역할](https://docs.oracle.com/en/java/javase/25/docs/specs/man/javac.html)

- PRD·대표 문제: `tools/redesigned_lessons/java_launch/draft-prd.md`
- 8스텝 문제·행동·선택지 초안: `tools/redesigned_lessons/java_launch/prototype.json`
- 실제 실행 검사: `python3 tools/verify-java-launch-prototype.py`
- 기계 판독 계획: `tools/redesigned_courses/java/backend-extension-plan.json`

PRD는 draft이며 정식 수업으로 등록하거나 승인됐다고 표시하지 않았다. 현재 앱의 20수업은 그대로다. 레포의 `docs/content-rules.md`는 “PRD와 대표 문제 초안을 함께 승인받은 뒤 정식 제작한다”고 정한다. 이 계획과 대표 문제를 검토한 뒤 첫 수업부터 정식 제작한다.

## 구현이 먼저 필요한 부분

현재 터미널 실습의 채점기는 파일을 UTF-8 텍스트로 읽는다. `.class` 같은 바이너리를 만드는 빌드 수업에 그대로 적용하면 안 된다. 첫 수업의 앱 구현 때 코드 편집·실제 작업 폴더·JDK 명령·바이너리 산출물의 상태를 함께 다루는 실행기를 추가해야 한다.

또한 파일이 이어지는 것과 셸 프로세스가 이어지는 것은 다르다. 환경변수·백그라운드 수업에서는 스텝 전환 때 몰래 export를 재실행하지 않고 실제 셸 세션의 생명주기를 보존해야 한다. 명령 기록에 특정 글자가 있다는 이유만으로 개념을 이해했다고 채점하지 않는다.

Gradle·DB·Kafka·AI는 각각 버전·준비 상태·실제 다운로드 진행·사용 자원·정리 방법을 확인한다. Docker 명령이 있다는 사실만으로 엔진이 실행 가능하다고 판정하지 않는다. 현재 첫 초안에는 어느 서비스도 설치하거나 실행하지 않았다.
