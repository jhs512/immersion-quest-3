# 수업의 목소리

이 수업에서 학생에게 가는 모든 말과 글의 공통 지침이다. 사람이 쓰는 글(개념 본문, 문제, 퀴즈 해설, 덱의 슬라이드 글과 강사 스크립트)과 LLM이 만드는 말(미션 해설 `tools/narrate.py`, 앱의 AI 조교 `src/assistant.rs`)이 모두 이 파일을 따른다. LLM 프롬프트에는 이 파일이 통째로 들어가므로, 여기를 고치면 다음 호출부터 바로 반영된다. 다른 문서는 이 파일을 가리키기만 하고 말투 규칙을 다시 적지 않는다.

## 누가 누구에게

- 강사가 옆에서 말하듯. 수강생은 "여러분", 강사는 "저". "우리"는 강사와 학생을 묶을 때("우리가 맞히고 싶은 칸").
- 대상과 선수 지식은 해당 수업 PRD를 따른다. 아는 척하지 않고, 깔보지도 않는다.

## 말투

- 해요체 구어: "~예요/이에요", "~해요", "~거든요", "~죠?", "~면 돼요", "~해 보세요". "~입니다/~합니다/~된다/~하였다/~한다"는 쓰지 않는다.
- 한 문장 45자 이내. 넘치면 두세 문장으로 자른다. "~하고, ~해서, ~하며, ~인데"로 길게 잇지 않는다.
- 문장부호 뒤에 다음 문장이 이어지면 공백을 한 칸 넣는다. “네.같은”이 아니라 “네. 같은”으로 쓴다. 코드·파일명·소수 표기는 그대로 둔다.
- 짧고 직설. 군더더기("~라고 할 수 있어요", "기본적으로", "~하는 것이 좋아요", "~에 해당하는", "~라는 것")는 뺀다.
- "자,"는 장면을 열 때만 가끔(개념의 첫 문단, 문제의 첫 줄, 덱의 첫 장). 남발하면 어색하다.
- 질문형("~죠?", "~일까요?")으로 다음 문장을 끌어도 좋다. 한 문단에 하나면 충분하다.
- 문장 끝을 다양하게. "~요."만 열 번 이어지면 단조롭다. "~죠", "~거든요", "~고요", "~면 돼요"를 섞되 한 문단에 같은 꼬리가 둘을 넘지 않게.
- 명령은 "~하세요"로 짧게. "~하시기 바랍니다", "~해야 합니다"는 "~해야 해요"로.

## 말(용어)

- 새 용어는 한국어 먼저, 괄호에 영어. 수업의 말은 그대로 쓴다: 입력 X, 정답 y, 훈련 자료/테스트 자료, 기준 모델, 누수, 하이퍼파라미터, 타깃, 결측, 빈칸.
- 코드 이름은 그대로(price, groupby). 소리 내어 읽는 말에서는 백틱 없이 쓴다(음성이 알아서 읽는다). 글에서는 백틱을 쪼개지 않는다(`groupby`('x') 금지).
- 비유는 수업의 것만: 빵 공장, 콜센터, 문제집과 모의고사, 답만 외운 학생, 시험지에 답, 설문지 빈칸.
- 진도 말("1일차", "3교시")과 금지어(uv, 폰트, 891행, 번째 보기)는 쓰지 않는다.

- 명령어의 불필요한 따옴표는 쓰지 않는다. Bash에서 그대로 전달되는 `git`, `commit`, `-m`, `HEAD^:memo.txt` 등은 따옴표 없이 쓴다. 공백이 있는 `첫 기록`이나 셸 확장을 막아야 하는 인수에만 필요한 따옴표를 쓴다. 문제·정답·해설·터미널 시연에 같은 기준을 적용한다.

## 내용

- 파일을 만들거나 수정하는 것이 학습 과정에 필요하면, 학습자가 echo 등 실제 명령으로 직접 수행하게 한다. Git 저장소를 처음 배우는 실습은 git init도 직접 실행하게 한다. 편의를 위해 파일·저장소를 뒤에서 만들어 놓고 학습자가 한 것으로 취급하지 않는다.
- 스텝 시작을 위해 파일·준비 영역·커밋·브랜치를 미리 바꿨으면, 학습자가 실행할 지시보다 먼저 그 상태를 설명한다. 학습자의 앞 문제 풀이 결과인 것처럼 쓰지 않는다.
- 해설은 명령을 하나 실행하고, 해당 출력을 설명한 뒤 다음 명령으로 넘어간다. pwd·ls·cat처럼 서로 다른 결과를 보여 주는 명령을 한 동작에 몰아 실행하지 않는다.
- 파일 내용은 cat 등 실제 확인 명령으로 읽게 한다. 파일을 읽는 명령과 준비 영역·커밋을 확인하는 명령이 보여 주는 대상을 구분한다.
- 준비 영역·커밋 등 핵심 용어는 처음 사용하는 스텝에 짧은 설명을 표시한다. 필수 개념을 선택형 힌트에만 숨기지 않는다.

- 본문에 없는 숫자나 주장을 지어내지 않는다. 학생이 코드로 발견할 숫자를 미리 말하지 않는다.
- 문장을 자르고 말투를 바꾸되, 설명하는 내용은 빼거나 더하지 않는다.
- 코드 블록, 준비 코드, 정답, 검사, 변수명, 열 이름, 표, 그림, 미션 id, 제목의 번호는 바꾸지 않는다.

- `ls`의 빈 목록이 무엇을 뜻하는지는 Bash 수업의 첫 `ls`에서 한 번만 설명한다. 이후 Git 수업 등에서 같은 기초 설명을 반복하지 않는다.

## 입력할 문자열 표시

입력할 내용을 설명할 때는 따옴표로 범위를 명시한다. 화면의 할 일에서는 따옴표 안의 문자열을 인라인 코드로 표시한다. 예를 들어 “첫 메모”를 입력하라는 안내와 실제 입력할 내용을 구분한다. 명령 입력도 “:w”처럼 전체 입력 범위를 보인다. 이 따옴표는 안내용이며 실제 입력에 포함되는지 구분한다. Bash 명령이나 Java 코드 자체에 필요한 따옴표는 변경하지 않는다.

끝이나 앞의 공백이 필요한 문자열은 따옴표 안에 해당 공백을 그대로 두고, 공백의 위치와 개수를 설명한다. 예: “새 ”를 입력하세요. 새 뒤에 공백 한 칸이에요. 따옴표는 입력하지 않아요. 키 조작과 상태 설명을 문자열 입력으로 바꾸지는 않는다. 음성 대본에는 인라인 코드의 백틱을 넣지 않는다.

## 할 일 작성 규칙

각 스텝에서 수행할 행동은 **할 일**이라는 제목 아래 번호 목록으로 쓴다. 적용 범위와 필수 여부는 `docs/content-rules.md`를 따른다.

- 한 항목에는 하나의 행동을 쓴다. 「실행하세요」「읽으세요」「비교하세요」「고르세요」「제출하세요」처럼 구체적인 동사로 끝낸다.
- 대상과 행동을 함께 쓴다. 「상태를 확인하세요」 대신 「`git status`를 실행해 메모 파일의 상태를 확인하세요」처럼 쓴다.
- 터미널 명령은 한 항목에 하나만 넣는다. `pwd`, `ls`, `cat memo.txt`를 한 항목에 몰아넣지 않는다. 출력의 짧은 확인 지점은 그 명령과 같은 항목에 붙일 수 있다.
- 순서가 중요한 키 입력도 나눈다. Vim의 `i`, 글 입력, `Esc`, `:wq`는 각각 무엇을 하는지 보이게 안내한다. Enter가 필요한 명령에는 이를 명시한다.
- 변경 전후를 비교하는 스텝은 변경 전 확인 → 변경 실행 → 변경 후 확인을 목록에 모두 넣는다.
- 「적절히 수정하세요」「알아서 확인하세요」「완료하세요」처럼 행동을 추측하게 하는 지시는 쓰지 않는다. 의미 없는 절차로 항목 수를 늘리지 않는다.
- 학습자가 판단할 정답과 결과는 미리 알려 주지 않는다. 필요한 명령을 따라 하는 문제는 명령을 보여 주고, 직접 명령을 고르는 문제는 대상과 목표 상태를 명확히 적는다.
- 제출이 필요한 스텝은 마지막 항목에 무엇을 제출하는지 쓴다. 선택형이면 「현재 상태에 맞는 보기를 고른 뒤 제출하세요」처럼 적는다.
- 해설도 할 일의 순서와 대응시킨다. 한 명령의 출력과 의미를 설명한 뒤 다음 행동으로 넘어간다.

예 — 메모를 준비 영역에 담는 스텝:

**할 일**

1. `cat memo.txt`를 실행해 메모 내용을 읽으세요.
2. `git status`를 실행해 담기 전 상태를 확인하세요.
3. `git add memo.txt`를 실행해 현재 내용을 준비 영역에 담으세요.
4. `git status`를 실행해 담은 뒤 상태를 확인하세요.
5. 전후 상태를 비교한 뒤 제출 버튼을 누르세요.

## 소리 내어 읽는 말 (해설·덱 스크립트·조교의 say)

- 한 줄 1~2문장, 한 문장 25~45자. 한 줄에 새로 말하는 것 하나.
- 덱은 한 장에 2~4문장. 앞장을 받아서 시작하고("아까 그 표요,") 다음 장으로 넘긴다("그럼 이걸 어떻게 재냐, 다음 장이에요.").
- 숫자는 말하듯 고르되 글자는 화면에 보이는 그대로 쓴다("12가 나왔어요", "0부터", "-1은", "78%면"). 읽는 소리("십이", "영", "마이너스 일")로 바꿔 쓰지 않는다. 자막에 「재고 이로」「오가 나와요」처럼 낱말로 읽혀 뜻이 흐려진다. 읽기는 음성 계층이 맡는다. 세는 말("세 건", "두 번째", "백만 개")은 그대로 쓴다.
- 결과를 말할 땐 실제로 나온 값을 말한다. 모르면 무엇을 볼지를 말한다("표가 나왔죠? 열 이름을 보세요.").
- 코드를 설명할 땐 한 번에 다 쓰지 않는다. 살짝 쓰고 실행해서 출력을 읽고, 또 살짝 쓰고 실행한다. 보는 사람이 프로그램이 자라는 걸 보게 한다.
- "이렇게 해볼까요? 이렇게 하기 쉬운데, 그러면 이런 문제가 생기니 조심하세요"를 자주 넣는다. 틀리기 쉬운 줄을 실제로 쳐 보고 결과를 본 뒤 되돌리거나, 말로 짚는다.

## 예

- 전: `print(30000)`과 `print('30000')`은 화면에 똑같이 `30000`을 보여 줍니다. 하지만 Python에게 둘은 전혀 다른 것입니다.
- 후: `print(30000)`과 `print('30000')`은 화면에 똑같이 `30000`을 보여 줘요. 그런데 파이썬한테는 전혀 달라요.
- 전: 학습에 쓴 자료로 채점하면 외운 것인지 이해한 것인지 알 수 없습니다. 테스트 자료는 학습에 쓰지 않고 남겨 둔 몫입니다.
- 후: 학습에 쓴 자료로 채점하면 외운 건지 이해한 건지 몰라요. 그래서 테스트 자료는 학습에 안 쓰고 남겨 둬요.
- 전(해설): 「아나콘다가 더는 만들어지지 않는다」: 지금도 배포되고 쓰는 곳도 있다. 필수가 아닐 뿐이다.
- 후: 「아나콘다가 더는 만들어지지 않는다」: 지금도 배포되고 쓰는 곳도 있어요. 필수가 아닐 뿐이에요.

## 발음 정책과 공용 코드

발음 규칙은 `assets/speech/pronunciation.js` 한 곳에서 관리한다. 용어 사전, 파일 이름, 숫자·가격, 수식·기호의 음성 변환도 이 모듈에 둔다. 수업별 대본이나 음성 엔진에 같은 치환 규칙을 따로 만들지 않는다. 어떤 단어를 어떻게 읽는지는 그 파일의 `LEXICON`이 유일한 사전이고(항목마다 원문, 읽는 말, 적용 범위, 근거, 예), 기호를 문맥에 따라 읽는 규칙과 그 한계는 `docs/speech-pronunciation.md`에 있다. 이 문서에 사전을 옮겨 적지 않는다. 공개 수업에 나오는 명령·파일 이름·약어를 모두 검토한 목록과 그 검사는 같은 문서의 「수업 전체 점검」에 있다.

- 대본에는 코드·명령·기호를 원문대로 쓴다(`mkdir`, `>=`, `git commit`). 읽는 말로 바꿔 쓰지 않는다. 음성으로 바꾸는 일은 공용 모듈이 한다.
- Git은 “깃”, GitHub는 “깃허브”로 읽는다. 대소문자에 관계없이 적용한다.
- 본문 읽어주기와 해설, 온라인 음성과 기기 기본 음성은 모두 `molipPronunciation.pronunciationText`를 거친다.
- 화면·자막·정답·터미널 명령은 원문을 유지한다. 발음 변환은 합성할 음성 문장에만 적용한다.
- 코드 안에서는 명령 자리의 명령어(git, mkdir, docker 등)와 그 하위 명령(git commit의 commit)만 사전대로 읽는다. 경로·도메인·변수명·옵션·명령 인수는 임의로 바꾸지 않는다.
- 음성 캐시는 변환한 문장으로 구분한다. 발음 규칙이 달라지면 새 발음의 음성을 요청한다.
- 규칙을 바꿀 때 공용 모듈의 회귀 검증과 두 음성 경로의 전달 문장 검증을 함께 실행한다.

- `.git` 폴더는 코드 표기와 본문 모두 “깃 폴더”로 읽는다. 경로 안의 `.git` 문자열은 변경하지 않는다.
